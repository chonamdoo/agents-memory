## 4. 보안: 팀 계정과 memory route는 별개

- coding host의 해당 회사 workspace에서 처리하는 행위

`no-training`, `no-public-disclosure`, `no-storage-outside-company`, `no-egress`를 같은 보장으로 취급하지 않는다. SaaS 추론 자체도 전혀 밖으로 나가면 안 되는 strict no-egress와 양립하지 않는다. 회사가 승인한 SaaS 처리 예외와 새 memory 저장 반출 금지를 분리해서 설정한다. strict profile은 승인된 내부 host·compute·모델이 있을 때만 가능하다.

서비스/worker는 목적별 허용 route를 명시하고 개인 provider env/key를 상속하지 않는다. 승인되지 않은 default/fallback, 모델 weight 첫 실행 다운로드, telemetry를 허용하지 않는다. 실제 반출 차단은 managed host·credential·OS/network 정책에서 집행한다. MCP token이나 `_meta.clientInfo`, bank tag, repo 경로만으로 이후 어떤 모델/계정에 답변이 보내지는지 증명할 수 없다. 회사 데이터를 자유로운 BYO client에 제공하면서 이후 목적지까지 통제한다고 약속하지 않는다.

agent-plane에는 DB·operator credential·규칙 publish 권한을 주지 않는다. loopback에도 설치별 인증과 endpoint identity, Host/Origin 검증이 필요하다. local UI의 승인 클릭이 같은 UID에서 위조 불가능한 인간 승인인 것처럼 표현하지 않는다. 강한 공유 승인은 별도 approver 권한이나 기존 사내 PR/IdP 정책으로 처리한다.

### HOME 분리 반례의 실제 관측

별도 0700 HOME 디렉터리 두 개, 다른 HOME의 0600 synthetic marker로 `/usr/bin/env HOME=... /bin/test -r ...`를 실행했다. 같은 OS UID 프로세스는 그 파일을 읽을 수 있다고 판정했다(exit 0). 실제 credential은 읽지 않았다. 임시 파일은 제거했다. **HOME 분리는 accidental config/capture 혼용을 줄이지만 같은 UID filesystem 격리는 아니다.** 다른 OS 사용자 또는 제품 sandbox의 차단을 시험한 것은 아니다.[관측](unified-home-boundary-smoke.json)

## 5. full memory loop와 영상에서 가져올 것

자동 capture → durable ingest → 신호·claim 추출/선택 → scope에 맞는 recall → 현재 유효한 근거를 사용한 reflect → 정정/철회 → 후속 작업에서 재사용을 유지한다. MCP tool로 수동 메모 몇 개 저장하는 것으로 이 요구를 대체하지 않는다.

- MCP는 대화 전체나 native memory 파일을 자동 수집하지 않는다. 지원 host의 승인 hook/event/export adapter가 필요하다. 첫 작업 전 recall, transcript 지연, interrupt, 실패/child event, 서비스 readiness를 각각 정의한다.
- envelope에는 host/session/root-run/agent/message/event ID, source span/digest/offset, snapshot·branch·유효 조건, 잘림/coverage를 남긴다. parent/child/handback/종료 export는 같은 episode가 중복 기록될 수 있으므로 재전송과 독립 반복을 구분한다.
- **codebase findings / human corrections / recurring investigations**를 구분한다. 인용된 AI 로그는 human correction으로 승격하지 않는다. 계획·permission approval·도구 실행 결과·사실 정정·규칙 수락은 다른 event다.
- 원문, AI 추출, 참고 메모리, candidate, 승인 rule, 실행 skill은 서로 다른 권위를 가진다. 반복 횟수·confidence·Jev 확률·typed schema는 승인을 대신하지 않는다.
- 오류·mismatch·correction을 다음 동작의 근거로 연결한다. trace를 저장한 것만으로 다음 run이 개선됐다고 주장하지 않는다. 거절한 candidate를 문구만 바꿔 계속 재제안하지 않으며 새 근거를 구분한다.
- 원문 영상의 2 cents/session은 발표자의 해당 작업 수치다. 우리 제품 단가나 token 절감량은 아니다. BAML은 선택 가능한 typed extraction 도구, Query BAML은 해당 호출 관측 도구다. Jev는 선택적 판단 서비스이며 기본 security/approval authority로 넣지 않는다.
- health check·stale detection·fourth input은 시연 기능과 후속 아이디어를 구분한다. 코드 변화는 재검토 근거이지 자동 공통 규칙 변경 권한이 아니다. hidden chain-of-thought는 수집하지 않는다.

사용자가 정정한 특정 앱의 codegraph 재사용·SQLite/FTS5 최소 구성안은 이 설계의 요구나 결론에서 제외했다. SQLite라는 일반 backend 대안을 금지한 것이 아니라, 다른 앱 설계를 이 memory 제품에 잘못 적용한 결론을 제외한 것이다.

## 6. 컨벤션과 skill: 정확한 세 적용 범위

새 candidate를 활성화하거나 범위를 바꿀 때 정확히 다음 세 가지를 제시한다.

1. **내 로컬·해당 프로젝트**: 이 PC/프로젝트에서 적용. 팀 배포·Git commit/push를 강제하지 않는다. 회사 자료면 여전히 회사 경계 안에 남는다.
2. **프로젝트 공유**: 해당 프로젝트의 권한자가 검토·승인한 revision을 배포한다.
3. **팀 공통**: 해당 팀의 승인 권한과 팀/project 바인딩을 확인한다.

로컬 추천은 선택 전 자동 적용이 아니다. 취소/미응답은 candidate만 보존한다. 권한이 구성되지 않은 옵션은 세 선택지에서 없애지 말고 사용 불가 사유를 표시한다.

기존 내용 갱신은 scope를 유지하지만 새 revision 승인 규칙은 유지한다. 대상 device/project/team 추가, selector/phase 확대, required 여부 등 실제 적용 조건 확대는 scope 문자열이 같아도 재선택·권한자 승인을 요구한다. 승인은 본문·조건·예외·대상·selector의 exact revision/digest에 결합한다. 승격 시 이전 로컬 활성 revision을 계속 별도 권위로 두지 않는다.

원문 정본은 scope별 하나다. 승인 bundle의 본문 정본, 활성/철회 ledger, native host projection은 역할을 분리한다. Git 파일·PG 행·Hindsight directive가 서로 독립적으로 '현재 팀 규칙'을 선언하지 않는다. host 캐시는 projection이며 activation 권위가 아니다.

## 7. root-free 전달과 context 예산

팀 공통 규칙도 root `CLAUDE.md`/`AGENTS.md`에 **본문·목록·import bridge를 새로 넣지 않는다**. 기존 사용자의 지침을 삭제하는 뜻은 아니다. 같은 긴 본문을 unscoped `.claude/rules`나 passive skill로 옮겨 startup에 모두 로드하는 것도 피한다.

- memory MCP는 소수의 고정된 짧은 도구/스키마와 instructions만 공개한다. 전체 memory/rule catalog를 접속마다 전달하지 않는다. host의 deferred discovery가 지원되면 사용하되 universal 지원이나 0 token을 약속하지 않는다.
- 필수 규칙은 승인 scope + task/phase + 예정/변경 path의 명시 predicate로 결정한다. 선택적 참고 memory만 semantic top-k로 찾는다. mandatory 원문이 예산을 넘으면 작업 분할/범위 조정 또는 보호 대상 행동 차단이지 규칙 누락이 아니다.
- task가 정해진 시점과 첫 보호 대상 행동 전에 필요한 원문을 전달한다. 새 path에서 미전달 필수 rule이 생겼다면 지원 hook/wrapper가 행동을 거절하고 규칙을 받은 뒤 재계획하게 한다. PreToolUse에서 context만 추가한 뒤 이미 생성된 첫 Write를 allow하면 사전 준수 보장이 없다.
- Claude scoped rules와 Codex의 명시 skill identity·지원 hook/wrapper는 다른 구현이다. Codex nested AGENTS를 일반 lazy path loader로 부르지 않는다. Bash/IDE/외부 writer도 matcher 경계를 벗어날 수 있으므로 검사 가능한 규칙은 lint/CI, 보안은 ACL/sandbox/egress로 집행한다.
- session×rule ID/revision delivery receipt로 재주입을 줄이되 compact/new-thread/resume에서 유효성을 다시 본다. 서버 cache TTL이나 token 폐기는 이미 transcript/context에 들어간 내용을 지우지 못한다. 긴급 철회는 managed 보호 행동/세션을 중단하고 새 context가 필요할 수 있다.

보편적으로 적용되는 필수 규칙의 내용까지 0 context로 만들 수는 없다. 줄일 대상은 **무관한 본문·전체 목록·반복 주입**이며, token 숫자는 startup/첫 recall/장기 세션/compact-resume와 backend 추론을 분리해 실제 host에서 측정해야 한다.

## 8. authority·worker·삭제·복구

한 canonical PG authority에 durable event/operation과 outbox를 묶어 commit한다. `accepted`는 durable commit 후 반환하며 `accepted≠queryable`, `unavailable≠empty`를 유지한다. 원문을 별도 object store에 놓는다면 원자성·orphan·retention을 별도 해결해야 하므로 기본은 PG/persistent disk 중심으로 둔다.

Hindsight를 채택하려면 wrapper 밖 내부 writer/reader/consolidation/reflect/mental model/directive/refresh/import 경로까지 통제 지점을 명시한다. source generation·승인 revision·deletion epoch·lease fencing/CAS를 실제 publication transaction과 합성 입력에서 확인한다. lineage가 불완전하거나 전체 근거가 철회된 파생물을 사용할 수 없게 한다. 최종 응답 post-filter만으로 이미 오염된 내부 합성을 정상으로 만들지 않는다.

같은 source 재import·오프라인 spool·늦은 worker·old backup으로 철회된 자료가 부활하지 않게 scope-bound source identity와 본문 없는 tombstone을 유지한다. restore는 과거 snapshot과 별도로 신뢰할 수 있는 최신 deletion head를 확인·재적용하기 전 공개하지 않는다. logical export/import를 point-in-time backup으로 부르지 않는다.

logical retraction, physical purge, backup retention 완료는 서로 다른 상태다. raw·derived·index·cache·spool·jobs·exports·rule projection을 범위에 포함한다. 이미 외부 모델에 전달된 context나 provider retention까지 원격 삭제할 수 있다는 보장은 하지 않는다.

## 10. MCP 2026-07-28과 SIE localhost

공식 protocol revision은 `2026-07-28`, SDK semver는 별개다. 공식 changelog/transport 문서와 Python SDK 2.3.0·TypeScript SDK 2.3.1 release를 확인했다.[M1–M4]

- 새 wire에서 initialize/initialized와 protocol session/Mcp-Session-Id가 없어지고 request metadata를 사용한다. application memory DB와 durable jobs는 여전히 상태를 가진다.
- `server/discover`는 필수 server method지만 모든 client의 새 handshake라는 뜻은 아니다. MRTR은 input-required interaction을 처리한다. 독립 server request 제거를 모든 notification/SSE 제거로 확대하지 않는다.
- `Mcp-Method`와 protocol version을 전달하고 `Mcp-Name`은 named methods에 해당한다. request-scoped SSE/POST subscriptions는 남는다. stdio도 남는다.
- `ttlMs/cacheScope`는 cache freshness이며 auth/revocation을 대신하지 않는다. Roots/Sampling/Logging 등의 폐기는 즉시 삭제가 아니고 earliest removal을 구분한다.
- SIE pinned package는 `mcp>=1.9,<2`다. SDK1의 `stateless_http=True`가 새 protocol 지원을 증명하지 않는다. local edge는 configured `SIE_BASE_URL` cluster를 호출하므로 모든 실제 처리가 local이라고 말할 수 없다. CLI 기본 bind와 DNS-rebinding 설정을 그대로 기업 기본값으로 복사하지 않는다.[M5]

### 실제 protocol/state smoke

공식 Python `mcp==2.3.0`으로 localhost real HTTP server와 temporary SQLite를 실행했다. client A가 synthetic note를 저장하고 종료한 뒤 별도 client B가 같은 note를 조회했다. 최종 실행 exit 0. 네 wire 요청에서 `2026-07-28`, method/name, namespaced metadata를 관측했고 initialize 및 request/response `Mcp-Session-Id`는 없었다. 이는 **protocol 무상태와 application DB 지속성이 양립함**만 입증한다. Hindsight 제품, native host protocol 협상, 보안·capture·company auth·token 절감·crash recovery는 시험하지 않았다. 최초 throwaway assertion은 plain dict 출력의 structured-content 가정을 잘못해서 실패했고 명시 Pydantic output schema로 수정한 최종 관측과 구분한다. temporary script/data는 제거했다.[관측](mcp-2026-localhost-verification.ko.md)

| 승인/컨벤션 | 세 범위 UI·exact revision·거절/재제안·활성/철회 ledger | local-only 및 공유 정책을 같은 모델로 처리 | 승인 피로와 정책 충돌, selector 확대 검사 |

Agent Flow의 전체 resolver·runner·worktree gates를 재사용하지 않는다. native Agent Skills 표준과 Agent Flow의 phase/reason selector를 같은 것으로 부르지 않는다. 독립 어댑터를 raw Claude Code/Codex에서 먼저 검증하고 Agent Flow는 같은 opt-in consumer로 둔다. MCP가 연결되는 web/mobile/IDE라도 capture나 첫 행동 전 rule 전달이 없으면 full automation 지원으로 표시하지 않는다.

## 13. 착수 전 확정할 검증 기준

아래는 미실행 acceptance이며 지금 통과했다고 표시하지 않는다. 수동/reflect-off/rules-only로 줄여 전체 제품이 완성됐다고 표시하지 않는다.

1. **company route와 경계:** 같은 public/synthetic 자료로 approved host의 정상 경로를 유지하면서 개인 endpoint·provider env·다른 project/client·fake loopback·operator/DB 접근을 거절한다. raw/derived/log/backup/skill과 실제 network egress를 확인한다.
2. **engine 재사용 가능성:** source/approval/deletion generation의 통제를 모든 commit/read/reflect/refresh/import 경로에서 보인다. 전체 grounding 철회·stale worker·old import·backup restore 후 부활이 없어야 한다. 이를 유지할 수 있는 patch 범위와 담당 책임을 확인한다. wrapper-only는 탈락이다.
3. **native host full loop:** pinned Claude/Codex 각각에서 cold start·MCP 지연·transcript 지연·interrupt·child 중복·실패·세션 종료 후 worker·다른 기기 recall을 관찰하고 coverage/accepted/queryable oracle을 일치시킨다.
4. **세 범위와 root-free:** cancel/미응답·위조 승인·revision 불일치·selector 확대·Git 없는 local 활성화·권한 없는 team 승격을 확인한다. root 수정 없이 새 파일/rename/glob/Bash/subagent/compact/resume에서 첫 보호 대상 행동 이전 전달과 행동 차단을 따로 확인한다.
5. **동일 조건 품질·비용:** 같은 model/embedding/corpus/token budget으로 no-memory, matched hybrid/RAG, 선택 engine의 후속 coding task를 비교한다. 한국어 부정·임시 예외·코드 식별자·사실성·출처·범위·false promotion·prompt poisoning을 포함한다. write/read/reflect/reprocess/host injection/human review/storage/운영을 합산한다. paper/vendor 숫자나 영상 단가를 목표 실측으로 쓰지 않는다.
6. **설치·업데이트·복구:** 회사 local과 개인 VM의 clean/offline install, 동시 client, migration interruption, update/rollback, reinstall/uninstall, restore를 실행한다. binary rollback≠schema rollback이며 config/data ownership 밖을 덮어쓰지 않는다. offline 모델·SBOM·license·signature/pins·installer 권한을 확인한다.

**최종 선택:** 서비스/PG/worker authority와 root-free rule plane을 분리하고, MCP·host adapter는 얇게 유지한다. engine은 검증 가능한 Hindsight 재사용을 우선한다. 이번 설계에서 확정할 수 없는 부분은 engine 내부 통제 변경의 유지 가능성과 실제 host 품질/비용이며, 이를 모른 채 engine 점수나 작은 구현 크기로 승자를 선언하지 않는다.

# 로컬 우선 설계 계약 — native 모델 토론의 반박 대상

상태: 구현 전 설계안 [INFERENCE]. 저장소에 현재 product runtime은 없다. 이 문서는 기존 제안의 요구를 줄이지 않고 호출·정확성·context·실사용 완료 기준을 구체화한다. 새 source 조사와 두 native 모델의 상호 반박으로 최종 설계를 확정한다. 코드 구현·회사 정책 승인·검색 품질 실측과 구분한다.

## 1. 범위와 보장

독립 설치 service/worker와 단일 PostgreSQL 권위, 얇은 MCP edge, Claude Code/Codex/omp 별 opt-in 어댑터. Agent Flow는 일반 consumer, framework core·installer·isolated reviewer에 memory 강제 없음. 로컬 full loop 완성 및 1~2주 실사용 뒤 같은 release를 개인 persistent VM으로 전환한다. cloud provisioning은 지금 하지 않으며 회사 corpus를 개인 cloud로 이동하지 않는다.

API/DB에서 보장할 것: 승인 범위·identity·revision·출처 검증, 같은 idempotency request의 같은 효과와 replay 의미, stale publish 차단, 명시적 operation 상태, 제한된 결과 크기, source/derived 철회·복원 불변식. LLM의 사실 추출·순위·자발적 호출·준수를 100% 보장한다고 하지 않는다. 모든 workflow와 prompt가 같은 API를 사용할 수 있어야 하지만 MCP 등록만으로 매 turn 호출이 생기지 않는다. 자동화는 실제 지원 hook/wrapper 계약과 readiness를 검증한 surface에서 제공한다.

전체 loop는 capture→durable ingest→signal/claim extraction→scoped recall→grounded reflect→correction/retraction→next task. 승인 route가 없으면 extraction/reflect blocked를 노출하고 그 환경을 full 지원으로 표시하지 않는다. tool-only/manual/rules-only로 full 기능을 대체하지 않는다.

## 2. 호출 모델

- Agent-plane fixed small tool set candidate: `memory_context`(recall/explicit reflect), `memory_inspect`(선택 item의 근거·상태), `memory_record`(명시 note/candidate), `memory_feedback`(정정/거절/철회 요청). capture/approval/publish/admin는 별도 인증 API/CLI/UI. 최종 이름·schema는 모델 토론으로 한 세트 확정.
- native hooks와 omp extension, workflow wrapper, 일반 MCP 호출이 모두 같은 domain command handler를 사용한다. host별 ingest/search/승인 정책을 별도로 구현하지 않는다.
- producer가 보내는 event와 모델이 보내는 note를 구분한다. 모델 tool은 `human/approved` 권위를 자가 선언할 수 없다. 사업 session/root-run은 domain lineage이며 MCP wire session을 복원하는 우회 수단이 아니다.
- 회사/personal/customer 경계의 deployment identity와 project binding을 operator가 등록한다. repo remote·CWD·bank name·_meta.clientInfo는 권한 근거가 아니다. client credential은 principal/allowed deployment/project/purpose에 결합한다.
- server가 project를 임의로 추측해 default/global bank를 고르지 않는다. 미등록/모호한 repo·worktree·prompt project는 `BINDING_REQUIRED`다. 새 repo/project alias는 operator action. prompt에 path/phase가 없으면 unknown 상태를 보존하고 task-neutral approved 규칙과 일반 evidence만 제공하며 보호 대상 행동 전에 target resolution을 요구한다.
- workspace/worktree/fork/branch/file revision은 provenance/적용 조건, scope는 권한·공유 범위다. 동일 project의 다른 branch facts를 현재 code truth로 보여주지 않는다. 과거 facts는 historical 태그·validity로 분리한다.

## 3. 일관성·동시성 불변식

1. `schema_version`, domain command type, binding reference, client operation identity, causal minimum watermark, correlation ID를 명시한다. auth/role은 verified credential로 결정한다. model/client payload의 actor/scope 플래그는 권한을 늘리지 못한다.
2. protocol JSON-RPC request ID, MCP connection/session, operation ID, source event ID, root-run/episode identity, idempotency key는 서로 다른 개념이다.
3. 같은 `(principal, binding, command, idempotency_key)` + 같은 payload digest는 동일 effect/operation receipt. 같은 key + 다른 digest는 `IDEMPOTENCY_CONFLICT`. retry/reconnect/cancel 후에는 먼저 operation 상태를 조회하거나 같은 key를 replay한다. 삭제·승인 같은 변이는 새 key로 눈치껏 반복하지 않는다.
4. 최초 durable ingest와 outbox 등록은 한 PG transaction. producer spool flush와 server accepted는 다르다. `accepted≠queryable`, `unavailable≠empty`, `partial≠complete` 상태를 API/UI로 유지한다. exact-once delivery 대신 at-least-once delivery + effect dedup.
5. 단일 job lifecycle owner. engine 자체 operation/queue와 제품 ledger가 각각 final state를 선언하지 않도록 mapping/commit 책임을 명시한다. lease expiry·fencing token·expected generation/version으로 늦은 worker commit을 거절한다.
6. caller logical root-run과 child/handback/export dedup. actor role, typed human source, quotations, code snapshot, span, truncation/coverage를 보존한다. 동일 run 5개 event는 recurring investigation 5회가 아니다.
7. `memory_context`의 source selection/rule activation/permission은 명시 watermark snapshot. 모델 호출을 DB transaction 안에서 기다리지 않는다. reflect 완료 및 전달 전에 current source/permission/deletion eligibility를 다시 확인하며 stale이면 bounded re-evaluation 또는 `CONTEXT_STALE`다.
8. 읽기 linearization 지점과 취소/철회 순서를 계약한다. 철회 ack의 watermark 이후 요청은 최소 그 watermark를 요구한다. 이전에 시작/전달된 context가 자동 회수된다는 보장은 하지 않는다. 보호 행동은 latest policy check와 context generation이 필요하다.
9. timestamps는 기록/표시에 쓰고 최신 승인·lease·복원 권위를 client wall clock으로 결정하지 않는다. UUID/source ID collision·순서 역전·offset 재사용·파일 교체를 검출한다.
10. role/purpose 변경, scope 확대, body/selectors/applicability 수정은 exact revision에 결합. cancel/미응답 candidate only. local-only에 Git/team approval 강제 없음. 프로젝트 공유/팀 공통은 권한 있는 publication만 활성화.

## 4. root-free와 context 비용

- root CLAUDE/AGENTS에 새 본문·목록·bridge 없음. 기존 지침 삭제 아님. 다른 eager file/passive skill에 전체를 옮기지 않는다.
- session connect/start에서는 memory/rule 본문 0. fixed small schema만 노출. startup 모든 project·rule name list를 넣지 않는다. schema·native wrapper·server instructions도 실제 비용으로 측정한다.
- 작업이 정해진 때 deterministic approved rule routing; normal prompt의 phase/path unknown을 model 추측으로 허가하지 않는다. path가 새로 생기면 first-action barrier로 required minimal original을 전달하고 재계획하게 한다. semantic top-k는 optional memory용.
- per-request response budget을 bytes와 host/tokenizer의 actual rendered tokens로 관리. mandatory 집합을 예산 때문에 자르지 않는다. optional 내용부터 제외하고 부족하면 `REQUIRED_CONTEXT_OVER_BUDGET` 및 split/stop. 장문을 byte 중간에서 잘라 부정/예외를 없애지 않는다.
- private adapter API 응답의 control/receipt와 model_text를 분리한다. MCP consumer가 structured content를 전부 볼 수 있으므로 MCP 응답은 최소 stamp/coverage/citation 등으로 제한한다. detail은 inspect/status로 필요할 때만.
- delivery cache key는 principal/binding/purpose/context-generation/rule-ID/revision/policy epoch. host module-global dedup을 child sessions에 공유하지 않는다. compact/resume/newthread/fork 시 재평가. authoritative receipt와 client known-items는 권한을 대체하지 않는다.
- trace→memory→same prompt→trace recursive capture를 막는다. injected content/tool echoes는 source=user correction으로 승격하지 않고 source link/derived lineage를 유지한다.
- 최초 규칙은 pre-read/plan 단계에서 전달. PreToolUse additionalContext+allow만으로 이미 생성된 Write를 통과시키지 않는다. deny-once receipt도 미래 준수 보장이 아니며 CI/ACL/sandbox와 구분한다.

## 5. service·engine·model route

같은 PG/persistent topology를 회사 local과 이후 개인 VM에 쓴다. session child가 PG/worker owner가 아니다. thin stdio는 service client로만 필요 host에 제공한다. loopback + per-install auth + endpoint identity/Host-Origin 검사. shared company approval/DB privilege는 agent credential과 분리. HOME 분리만으로 같은 UID 격리를 보장하지 않는다.

Hindsight는 재사용 우선 후보지만 internal read/reflect/refresh/write/import가 canonical generation/retraction을 확인하는 bounded integration이 실제 source상 가능한지 평가한다. wrapper output-filter로 내부 합성 오염을 해결하지 않는다. 이를 유지할 수 없으면 단일 narrowPG core로 교체한다. 두 generic engine 병행·새 graph·Neo4j·Redis/object-store 기본 추가는 하지 않는다.

회사 approved Claude/Codex host는 유지. 새 worker/headless observer/API/embedding/reflect route는 별도 승인. allowed routes manifest·clean env·offline imported weights·no personal fallback·no implicit download/telemetry. native app-server/CLI 제공 기능과 회사 사용/구독 권한은 별개. no-training/no-storage/no-egress를 혼동하지 않는다. 클라우드에는 같은 제품 profile+TLS/IdP/approved routes만 추가; 지금 cloud 환경 부족은 local 검증을 막지 않는다.

## 6. 운영·설치·삭제

설치·project binding·host opt-in·service start는 별도 단계이며 global host config/rules 자동 overwrite 없음. owned config entry만 관리, uninstall은 data 보존이 기본이고 explicit purge는 별도. supervisor 하나, migration lock, readiness 구분, status/doctor에 capture watermarks·queue/blocked/error·protocol/capability/version 표시. service unavailable시 optional recall은 unavailable로, required protected action은 fail closed.

local spool bounded/권한/retention/backpressure·디스크 부족·무효 credential·permanent malformed job·retry exhaustion·crash recovery를 계획한다. queue는 durable PG, 다른 generic queue 기본추가 없음. 데이터·raw/derived trace 최소화; 본문은 삭제 가능 storage, immutable audit/tombstone에 삭제 본문 복제 금지.

forget/retract/physical purge/backup retention 완료를 분리. source·derived·index·cache·spool·job·exports·rule projections와 다시 import/replay되는 source identity를 통제. 과거 backup만으로 latest deletion head를 잃지 않는다. 복원 후 reconciliation 전 service 공개 금지. image rollback≠schema rollback. signed/pinned artifacts+SBOM/model/license/offline-model tests와 dataset versions, model prompt/parser/index generation 변경 시 reprocess 책임.

## 7. 로컬 구현·1~2주 실사용·cloud 전환

실행 순서의 완료 조건은 scope가 아니라 의존 관계다: contract/authority 결정→domain/PG durable operations/eligibility→통제된 engine/approved route→thin MCP와 three native host adapters→capture/rule/reflect/feedback/forget/restore 전체 smoke→local trial→cloud same release.

local completion은 Claude/Codex/omp 각각 normal prompt+workflow, new/resumed/compacted/forked sessions, same project cross-host recall, simultaneous writers/readers, error/cancel/replay, first-new-file rules, no-root-change, no-other-project/customer ingress, no-external unapproved inference, derived retraction/restore 전체 결과를 의미한다. source/docs만으로 runtime pass라고 쓰지 않는다. Agent Flow 없는 실행이 먼저 통과해야 한다.

trial은 개인 synthetic/public projects부터 시작, 회사자료는 별도 승인 후. 1~2주라는 날짜만 채우면 pass가 아니다. memory-on vs no-memory/동일조건 baseline을 비슷한 coding/review/일반질문 task로 관측: startup/turn/recall rendered tokens·extra roundtrips·p50/p95 local latency·candidate accept/reject/false promotion·중복/누락/blocked 작업·영구 실패·실제 후속 수정 품질·route/cost·운영시간. 수치 target은 측정 전 proposal로 표시하며 제품 성능으로 보고하지 않는다. 권한 혼선·반출·철회 부활·필수규칙 우회·silent capture gap이면 trial 중단/rollback. baseline root/user instructions와 private projects는 침해하지 않는다.

cloud 진입 조건은 local full acceptance와 trial guardrails 통과, same artifact/schema/policy semantics, persistent VM/TLS/auth/backup/restore 및 개인 route 결정이다. 지금 cloud account/infra를 만들지 않는다. 차후 데이터 이동은 개인 corpus의 명시 export/import 및 최신 deletion head·compatibility 검증; 회사 corpus는 이동하지 않는다.

## 8. 설계 산출물과 추가 검토 범위

최종 architecture와 domain/schema/command/result/error/operation-state 계약, scope/rule precedence, host/version/capability support matrix, local module/dependency structure, implementation milestones/acceptance matrix, token-budget instrumentation, install/update/runbook, local trial log와 cloud handoff 기준을 하나의 문서 세트로 연결한다. native model별 peer 반박·채택/기각·남은 disagreement와 실제 process/model/effort/input/output hashes를 보존한다.

추가 위험: same-UID credential/approval 접근, MCP2-only vs legacy host handshake, branch/worktree aliases, reused root-run IDs, schema/index/model drift, conflict/exception precedence, Unicode/한국어 부정·code identifier, recursion/poisoning, rate/resource budgets, observer effects, credential revocation/offline lease, disk/PG/worker failure, updates/rollback/restore source resurrection, supply-chain/licensing, provider retention and context already delivered. 위험마다 실제 domain/adapter/operations 책임과 acceptance를 매핑하고 무관한 multi-cloud/SaaS/HA scope는 추가하지 않는다.

# 다중 host 통합: MCP wire·hook·lifecycle 근거 보고 (조사일 2026-10-12)

범위: 공식 문서·고정 source의 계약만 다룬다. 실제 runtime 성공, 제품 구현, native model 리뷰가 아니다. omp 문서는 설치본 기준(18.3 이상, 정확한 버전 미기록). Claude 문서는 버전 표기가 없고 v2.1.295까지 언급한다. Codex 문서도 버전 표기가 없다.

## A. 근거 사실 12개

**F1 omp는 legacy MCP client다.** `connectToServer()`는 initialize를 `2025-11-25`로 보내고 roots를 광고하며, `ping`과 `roots/list`에 응답한다(omp://mcp-runtime-lifecycle.md "Connection establishment"). 설치 문서 전체에 `2026-07-28`, `server/discover`, `resultType`이라는 표기가 없다. legacy `sse`는 2024-11-05다. 영향: 2026 전용 server에 연결하면 실패할 가능성이 높다 [INFERENCE: spec matrix 기준].

**F2 spec이 legacy client를 위한 합법적 경로를 정해 둔다.** versioning.md의 Compatibility Matrix 기준이다.
- Legacy client + Modern server는 실패, Legacy client + Dual-era server는 동작한다.
- dual-era server는 두 era를 같은 endpoint나 process에서 동시에 제공할 수 있다(MAY).
- initialize를 받으면 legacy semantics를 그 stdio process나 HTTP session 범위에서 적용한다.
- modern-only server는 initialize 오류에 지원 version을 적어야 한다(SHOULD).
- `serverInfo`는 보안 판단에 쓰면 안 된다(SHOULD NOT, discover.md).
- 끊긴 stream은 새 request ID로 다시 보내야 하며(MUST), `Mcp-Session-Id`는 제거됐다(changelog Major 1·9).
- 따라서 JSON-RPC id나 session은 idempotency key나 identity가 될 수 없다. cross-call state는 server가 발급한 handle을 tool 인자로 넘긴다.

**F3 host마다 MCP era가 다르다.**
- Claude Code: v2 runtime은 TS SDK 2.0 기반이며 2026-07-28을 지원한다. server에 지원 여부를 묻고, 지원하지 않으면 v1처럼 연결한다. feature flag를 가져오는 session은 v2.1.232 이상, 그 밖은 v2.1.274 이상에서 기본값이다. `MCP_PROTOCOL_NEGOTIATION=legacy`로 강제할 수 있다(code.claude.com/docs/en/mcp "MCP client runtimes").
- Codex: 문서는 initialize의 instructions를 쓴다고만 적고, 앞 512자를 권장한다. source commit `f2bee854`(2026-07-28)가 discovery, MRTR, legacy fallback(test 기준 2025-06-18)을 추가했다. 이 commit은 이전 조사에서 고정한 0.162.1 source `092d3acd`의 조상이다(GitHub compare 결과 ahead, behind 0). 설치본의 실제 runtime 동작은 확인하지 않았다.

**F4 model 입력 전 hook.**
- Claude `UserPromptSubmit`: `additionalContext`를 prompt 옆에 붙이거나 block할 수 있다. 기본 timeout은 30초이고, timeout이면 context는 버려지고 prompt는 그대로 진행된다. 막으려면 `onFailure:"block"`(v2.1.295 이상)이 필요하다. 사용자가 입력한 prompt 외에 scheduled task, background subagent 보고, 다른 session의 message에도 실행된다.
- Codex `UserPromptSubmit`: developer context를 추가하거나 block할 수 있고, matcher는 지원하지 않는다.
- omp:
  - `before_agent_start`는 일반 prompt와 dequeue된 batch마다 실행되며 같은 제출에 대해 재진입할 수 있다(최대 3회 시도). handler의 외부 side effect는 롤백되지 않는다.
  - `context`는 LLM 호출마다 message를 교체하고 저장하지 않는다.
  - `input`은 interactive와 RPC에서만 실행되고 print와 ACP에서는 실행되지 않는다(omp://extensions.md "Prompt and turn lifecycle").

**F5 tool 직전 차단과 context 전달 시점.**
- Claude PreToolUse: precedence는 deny > defer > ask > allow이고 deny 사유는 Claude가 본다. `additionalContext`는 tool result 옆에 붙는다. 사용자 정의 deny·ask rule은 hook 결과와 관계없이 계속 평가된다. `if` 필터는 best-effort이므로 강제가 필요하면 permission rule을 쓰라고 안내한다. timeout은 기본적으로 차단하지 않는다.
- Codex: deny, exit 2, legacy block을 지원한다. `updatedInput`은 allow와 함께일 때만 받는다. `ask`나 `continue:false`를 반환하면 hook이 실패로 처리되고 tool은 계속 실행된다. hosted tool(WebSearch 등)에는 hook이 없다. 문서 스스로 'complete enforcement boundary가 아니다'라고 쓴다.
- omp `tool_call`: block에서 short-circuit하고 handler throw나 timeout은 fail-closed다(30초). `additionalContext`는 tool이 실제로 실행되어 오류 없이 끝났을 때만 결과 뒤에 전달된다.
- 결론: context를 붙이고 allow하는 방식은 첫 쓰기 전에 규칙을 전달하지 못한다. 실행 전에 규칙을 보장하는 수단은 deny와 사유뿐이다.

**F6 compact·resume·fork 신호.**
- Claude:
  - `SessionStart`의 source는 startup·resume·clear·compact·fork다. v2.1.214 전에는 fork가 resume으로 보고됐다.
  - 주입한 text는 transcript에 저장되고 resume 때 hook을 다시 실행하지 않고 replay한다(값이 stale해질 수 있음). context를 회수할 수 없다는 근거다.
  - PreCompact는 block할 수 있고, PostCompact는 관찰만 한다.
  - skill은 compaction 뒤 skill당 5,000 token, 합계 25,000 token까지만 다시 붙는다.
- Codex:
  - SessionStart의 source에 fork가 없다.
  - compact 뒤 `source:compact`가 다음 요청 전에 실행되며 turn 중간에도 실행된다.
  - `thread/fork`는 새 id와 `forkedFromId`를 주지만 `sessionId`는 root 것을 유지한다(app-server.md).
- omp:
  - compact: `session_before_compact`(cancel 또는 교체), `session.compacting`(context, preserveData), `session_compact`.
  - fork: `session_before_switch`/`session_switch`를 reason fork로 내보내고, 새 id와 `parentSession`을 가진다. entry fork는 `session_branch`를 reason fork로 내보낸다.

**F7 child 상태 분리.**
- omp:
  - factory는 subagent마다 다시 bind되지만 module-level 변수는 공유된다(extensions.md L67).
  - `ctx.agent`(`kind`·`id`·`name`·`depth`·`parentId`)를 key로 써야 한다.
  - child는 parent의 MCP 연결을 공유하는 proxy를 쓴다(tools/task.md L190). server는 연결만으로 parent와 child를 구분할 수 없다.
  - `session_stop`은 subagent에서 발생하지 않고, `before_subagent_spawn`은 model 선택과 block만 할 수 있다.
- Claude:
  - tool hook에 `agent_id`와 `agent_type`이 들어온다.
  - SubagentStart context는 이미 child context에 있으면 다시 넣지 않는다.
  - fork가 아닌 subagent는 새 context에 CLAUDE.md 계층을 받는다(Explore와 Plan은 제외). fork는 전체 대화를 상속한다.
  - 이름으로 참조한 `mcpServers`는 parent 연결을 공유한다.
- Codex: subagent hook의 `session_id`는 parent 것이다. SubagentStart context는 child의 developer context로 들어가며 child 시작을 막을 수 없다. mcp_servers와 skills.config는 따로 지정하지 않으면 상속된다.
- 결론: 세 host 모두 session id만으로는 child나 fork lineage를 유일하게 식별할 수 없다.

**F8 출력 소유권, 동시 실행, 예산.**
- Claude: 여러 hook의 `additionalContext`가 모두 전달된다. 10,000자를 넘으면 파일로 넘기고 앞 2,000자 preview만 준다. async hook은 결정을 내릴 수 없다.
- Codex: 같은 event에 걸린 command hook을 동시에 실행한다. `additionalContext`가 약 2,500 token을 넘으면 temp 파일로 넘긴다. background hook은 session당 최대 8개다. MCP tool hook은 연결을 새로 만들지 않고, 오류가 나도 차단하지 않는다.
- omp: `tool_call`의 `input`은 마지막 handler 값이 적용되고, 같은 내용의 context는 중복 제거된다. `before_agent_start`는 첫 message만 유지한다.

**F9 관리자와 trust 설정이 hook을 무력화할 수 있다.**
- Claude:
  - `allowManagedHooksOnly`가 켜지면 user, project, local, plugin hook이 막힌다.
  - settings hook은 workspace trust를 확인한 뒤 실행된다.
  - SessionStart 시점의 `mcp_tool` hook은 launch 때 skip된다. command hook을 써야 한다.
- Codex:
  - 관리되지 않는 hook은 hash 기준으로 trust 받아야 실행된다.
  - project hook은 project가 trusted일 때만 실행된다.
  - `requirements.toml`로 hooks를 끌 수 있다.
- 회사 환경에서는 hook capability가 none일 수 있다.

**F10 schema 공개 지연과 hidden metadata.**
- Claude: tool search가 기본이라 처음에는 tool 이름과 server instructions만 load한다. 설명과 instructions는 2,048자에서 자른다. `_meta` key로 `anthropic/alwaysLoad`, `anthropic/maxResultSizeChars`(최대 500k), `anthropic/requiresUserInteraction`가 있다.
- omp: discoverable tool을 `xd://` catalog로 보이고 문서는 필요할 때 읽는다(settings.md L616-617). server instructions를 system prompt에 4,000자까지 붙인다. tool 호출 전에 `i` 필드 제거, 값이 빈 optional 생략, `local://`를 실제 경로로 바꾼다.
- vendor `_meta`는 host마다 다르다.

**F11 재전송 위험.**
- omp: MCPTool과 DeferredMCPTool은 retriable 연결 오류가 나면 reconnect 뒤 1회 재시도한다. 수락된 SSE POST 이후에는 다시 보내지 않는다. stdio는 자동 재시작하지 않고, manager가 backoff(0.5s→4s) 뒤 연결하며, 30초 안에 5회를 넘으면 circuit breaker가 작동한다.
- MCP 2026에서는 재전송할 때 request ID가 바뀐다.
- 따라서 상태를 바꾸는 operation에는 domain idempotency key가 필수다.

**F12 omp 규칙 파일 경로는 root-free 원칙과 맞지 않는다.**
- rulebook은 이름과 설명을 system prompt에 바로 나열하고, alwaysApply는 본문 전체를 바로 주입한다.
- TTSR은 stream을 끊고 주입하며, rulebook의 globs는 권고일 뿐 강제되지 않는다(rulebook-matching-pipeline.md §5-7).
- 승인된 규칙을 `.omp/rules`로 내보내면 eager listing이 생기거나 권위 있는 사본이 둘이 된다. 기본안으로 부적합하다.

## B. 공통 capability 어휘 [제안]

각 capability의 상태는 `native`, `partial`, `none`, `unknown` 중 하나이며, host·version별 manifest로 선언한다.

- `ctx.prompt`: model 입력 전 per-turn context
- `gate.prompt`: prompt 차단
- `ctx.session{startup,resume,clear,compact,fork}`: session 시작과 재평가 trigger

- `tool.rewrite`: tool 입력 교체

- `ctx.child`: subagent 시작 context
- `lineage{session,agent,turn,tool_call}`: 식별자
- `fail_mode{open,closed,configurable}`: hook 실패 처리
- `ctx.persisted{replay,ephemeral}`: 주입한 context의 저장 여부
- `mcp.era{legacy,modern,dual}`: MCP era
- `capture.turn_end`: turn 종료 시 capture

## D. 오래된 initialize client를 위한 명시적 edge

omp, Claude v1 runtime, `MCP_PROTOCOL_NEGOTIATION=legacy`, Codex fallback 경로는 initialize를 쓴다. 이들은 dual-era server나 별도 legacy stdio edge에 붙을 수 있으며, spec은 Legacy + Dual-era를 동작하는 조합으로 정한다(versioning.md).

조건은 다음과 같다.
- 두 edge 모두 같은 domain operation, schema, handle, idempotency key, auth binding을 써야 한다.
- legacy session이나 `Mcp-Session-Id`, `clientInfo`를 identity, 권한, worker 상태로 쓰지 않는다.
- edge가 다르면 지원 범위를 다르게 선언한다(예: legacy edge에서 MRTR 없음).
- modern-only 배포가 omp에서 실패하는 것은 정상 결과다. 'v2만으로 모든 host와 호환'이라고 주장하지 않는다.

## E. 일반 prompt에서 project·phase·path를 모를 때 [제안]

- project: hook의 cwd를 git root로 해석해 정한다. 해석이 안 되면 `scope_unresolved`를 반환하고 화면에 보이게 한다. 개인 scope로 fallback하지 않는다.
- phase를 모르는 것을 wildcard로 취급하지 않는다. phase 조건이 있는 mandatory는 보내지 않는다.
- path 조건이 있는 mandatory는 첫 실제 path가 정해질 때 `gate.tool.deny`로 처리한다.
- optional semantic 결과는 별도 예산 안에서만 보낸다.
- 이미 전달한 rule ID와 revision은 lineage watermark로 중복을 막고, compact·resume·fork 때 다시 평가한다.

## F. local 수용 시나리오 [제안, 실행하지 않음]

1. dual-era stdio에서 omp initialize client와 modern client가 같은 operation을 호출하면 결과 digest와 revision이 같다.
2. modern-only server에 legacy client가 initialize를 보내면, 오류에 지원 version이 적혀 있다.
3. commit 뒤 응답이 유실되면, request id가 새로 바뀌어도 key가 같으면 durable record는 하나만 생긴다.
4. stdio의 `notifications/cancelled`와 HTTP stream 종료가 완료와 경합해도 반쯤 commit된 상태가 생기지 않는다.
5. host 3개에서 path 없는 일반 prompt를 처리할 때 phase·path 조건 rule은 빠지고 응답은 예산 안에 든다.
6. 첫 쓰기 시도는 deny와 rule ID·digest를 받고, watermark 확인 뒤 allow된다. allow와 context만 붙인 경우는 전달로 세지 않는다.
7. Claude의 compact·fork, Codex의 compact, omp의 compact·fork 뒤 watermark를 다시 평가하고 중복을 막는다.
8. omp module 변수에 상태를 저장하지 않는다. `ctx.agent`, Claude `agent_id`, Codex `agent_id` 기준으로 child 상태가 분리된다.
9. hook timeout이 나면 Claude는 fail-open하고 omp는 fail-closed한다. 어느 쪽이든 결과에 degraded로 표시한다.
10. company와 personal route를 adapter 설정으로 선택하고, `serverInfo`나 `clientInfo`로 정하지 않는다.

## G. 금지할 과대주장

- 모든 host가 MCP 2026을 지원한다, 또는 v2만으로 모든 host와 호환된다.
- hook 출력이 model 준수를 보장한다, 또는 allow와 context가 첫 쓰기 재계획을 보장한다.
- PreToolUse가 보안 경계다.
- session_id는 child나 fork마다 유일하다.
- 한번 주입한 context를 회수할 수 있다(Claude는 resume 때 replay).
- Claude SessionStart 시점에 mcp_tool hook을 쓸 수 있다.
- Codex hook이 hosted tool도 잡는다.

## 2. "싼 fork" 가정의 가장 강한 반례
fencing과 즉시 철회를 보장하려면 poller 한 곳이 아니라 모든 write 경로를 고쳐야 합니다.
- 대상 경로: retain의 여러 batch TXN, consolidation의 batch별 commit, refresh, import, delete.
- source가 직접 기술한 문제: orphan consolidation이 scope lock 불변식을 깹니다(consolidator L84-89).
- 현재 이 경로들은 claim 세대를 읽지 않습니다.
- decommission과 cancel은 살아 있는 stale worker를 멈추지 못합니다. 결과는 중복 LLM 비용과 상태 덮어쓰기입니다.
- restore는 같은 schema에 있는 invalidate, delete, 작업 상태까지 backup 시점으로 되돌립니다. 철회 자료가 부활하고 작업이 재실행됩니다.
- 패치 대상이 1.18MB 단일 모듈과 약 100개의 alembic version이라 충돌면이 큽니다.

역방향 반례도 있습니다. 단일 노드, 단일 worker, 같은 content 재retain 조건에서는 content_hash gate가 data 중복을 대부분 흡수합니다. 그래서 local 단계는 fork 없이도 운영할 수 있습니다.

## 3. 권장: bounded reuse [제안]

### 구성
- 엔진: Hindsight pin을 unforked로 사용합니다.
  - `MCP_ENABLED=false`, 고정 `WORKER_ID`, API 내장 worker 1개.
- 권위: amm schema(같은 cluster)에 둡니다.
  - capture_event(append-only): event_id, trust_domain, host/session/root-run/agent lineage, actor, source_uri, byte hash, generation
  - outbox: lease, fencing token, generation
  - receipt(operation_id)
  - state: candidate/approved/rejected, 3-scope, exact digest
  - tombstone
- amm이 Hindsight에 쓰는 유일한 writer입니다.

### Retain
- `document_id=amm:{event_id}:{rev}`로 고정하고 replace만 씁니다. append는 금지합니다.
- metadata에는 비권위 사본만 넣습니다.
- receipt를 잃으면 같은 document를 다시 제출합니다. 같은 content라면 Hindsight gate가 흡수합니다.
- 완료 확인: GET operations/{id} + loopback retain.completed webhook(at-least-once).
- lease를 잃거나 generation이 바뀌면 DELETE operations/{id} 후 결과를 재검증합니다.

### Eligibility
- `scope:*`·`state:*` tag를 resolve_tag_scope로 엔진 안에서 강제합니다.
- 승격이나 범위 변경은 amm 승인 후 document tags PATCH로 반영합니다.
- 그 operation이 완료되기 전까지 watermark로 해당 doc 읽기를 막습니다.
- 승인된 rule/skill 본문은 amm selector로 결정적으로 전달합니다. directive는 쓰지 않습니다.
  - agent principal의 directive CRUD는 validate_bank_write로 거부합니다.
- reflect 호출 시 `apply_all_directives=false`, `include_based_on=true`로 고정하고, 결과는 candidate로만 다룹니다.
- `observation_scopes` 확장은 쓰기 범위 검사로 거부합니다.

### 철회와 restore
- 처리 순서:
  1. tombstone head 기록
  2. invalidate/delete 실행
  3. retraction pending 동안 해당 observation과 mental model 읽기 차단
  4. 필요하면 observations clear 후 refresh
- restore 대응:
  - restore마다 generation을 올립니다.
  - tombstone은 backup에서 빼고 banks FK도 두지 않습니다. 그래야 TRUNCATE에 영향받지 않습니다[bank_tables 문서에서 추론].
  - tombstone을 다시 적용한 뒤에만 읽기를 엽니다.
- spool replay는 event_id로 중복을 제거합니다.

### 권한 / 정리
- DB role 분리: migration(`MIGRATION_DATABASE_URL`), app, amm, read-only reviewer.
- `ENABLE_BANK_CONFIG_API=false` 또는 get_allowed_config_fields가 빈 set을 반환하게 합니다.
- dry-run, OCR parser는 끕니다.
- TenantExtension으로 token→schema/allowed_bank_ids를 묶고, validator로 principal→읽기/쓰기 범위를 정합니다. bank-wide 작업은 operator만 합니다.
- purge 절차: document 삭제 + history orphan sweep + trace/audit 보존기간 정리 + backup 만료. tombstone에는 본문을 넣지 않습니다.

### Fork patch가 필요한 조건
- multi-worker fencing이 필요할 때
- invalidate 결과를 동기적으로 cascade해야 한다고 보장할 때
- 엔진 audit에 actor가 필요할 때

### 대안: narrow PG core로 교체하는 조건
- extension API가 pin 업그레이드 사이에 깨질 때
- shared observation, internal background, untagged directive 경로를 막을 수 없을 때
- 승인된 LLM의 한국어 추출 품질이 기준에 못 미칠 때
- 교체하더라도 capture→…→next task 전체 흐름을 같은 계약으로 대체해야 하며, 기능 축소는 허용하지 않습니다.

# Python MCP 2.x: 같은 localhost endpoint의 modern·legacy 호출 확인

## 결정과 범위

**Python 3.12 + 공식 `mcp==2.3.0`을 서비스 언어·MCP SDK 후보로 채택할 수 있다.** Python으로 MCP `2026-07-28`을 구현하는 데 TypeScript 서버가 선행 조건은 아니다. 호스트 플러그인은 해당 호스트의 언어를 써도 서비스 API와 의미 계약은 하나다. SDK major version과 wire version은 별도 표기한다.

이는 제품 구현 완료 판정이 아니다. 현재 저장소에는 조사·설계 문서만 있다. Python SDK/HTTP 연결의 실측과 Hindsight/PG/실제 Claude·Codex·omp의 제품 연결 증거를 구분한다.

## 공식 근거

- [Python SDK protocol versions](https://py.sdk.modelcontextprotocol.io/protocol-versions/): `Client(..., mode="auto")`는 `server/discover`를 사용하고 구형 서버에서는 initialize로 fallback한다. `mode="legacy"`는 같은 서버와 handshake-era 연결한다. `mode="2026-07-28"`은 버전을 pin하므로 discovery 없이 시작하고 서버 신원·capability가 자동 확인되는 것은 아니다.
- [Python SDK ASGI app](https://py.sdk.modelcontextprotocol.io/run/asgi/): `MCPServer.streamable_http_app()`은 Starlette/ASGI app을 반환한다. 단독 앱은 lifespan을 관리한다. 다른 앱에 mount할 때 top-level lifespan에서 `mcp.session_manager.run()`을 관리해야 한다. localhost Host/Origin 보호는 endpoint 인증을 대체하지 않는다.
- [SDK legacy-clients](https://py.sdk.modelcontextprotocol.io/run/legacy-clients/): 하나의 앱으로 두 protocol era를 제공한다. `stateless_http` 옵션은 legacy 동작의 설정이고 modern 요청의 무상태성은 별도이다.
- [공식 Python SDK v2.3.0 고정 소스](https://github.com/modelcontextprotocol/python-sdk/tree/2118f14f8a19bc158d8a1cf90af58d85d187f849): 조사 시점의 버전·전송 소스 근거. 라이브 문서가 앞으로 변할 수 있으므로 설치 lock과 host matrix를 함께 관리한다.

## 이번 실제 실행

## 설계 반영

1. 하나의 공식 Python SDK edge에서 modern과 legacy를 처리하고 **같은 domain handler**를 호출한다. 별도 구형 엔진·의미 shim을 만들지 않는다.
2. 제품의 operation/episode/source revision은 MCP transport session ID나 JSON-RPC request ID에 의존하지 않는다.
3. Modern 연결을 쓴다고 tool catalog·description·rule body의 모델 토큰 비용이 사라지지 않는다. 연결 시 corpus/rule body 0, 작은 고정 catalog, 실제 작업에 필요한 bounded context를 별도로 설계한다.
4. pinned mode의 무왕복은 endpoint 인증이나 capability 검증을 생략해도 된다는 뜻이 아니다. 인증된 endpoint identity/host compatibility와 cache invalidation은 별도다.
5. 실제 native 호스트의 HTTP/stdio, hook, compaction·fork·subagent, timeout/retry 동작은 **각각 제품 acceptance scenario에서 검증**한다. Python client가 legacy mode로 통과했다는 사실만으로 omp/Claude/Codex 연결 완료라고 쓰지 않는다.
6. 첫 로컬 제품은 위에서 실행한 Python 3.12 계열을 대상으로 lock한다. OS 기본 Python 3.9에 맞추기 위한 SDK downgrade는 하지 않는다. 실제 지원 Python 최소 버전·dependency 충돌은 packaging milestone에서 pinned metadata로 확정한다.
7. 이후 cloud에서도 같은 ASGI app과 core를 쓰되 개인 deployment의 TLS/IdP/backup을 추가한다. Modern stateless 요청과 legacy in-process session의 scale-out 조건은 다르므로 무조건 다중 replica 호환이라고 주장하지 않는다.

## 1. Hindsight를 기본 엔진에서 제외하는 이유

Hindsight의 retain/recall/reflect 재사용 이익은 분명합니다. 그러나 현재 요구는 검색 결과를 마지막에 걸러내는 수준보다 강합니다. **잘못된 출처가 내부 추론에 들어가지 않고, 늦은 작업이 철회 이후 새 파생물을 publish하지 않아야 합니다.**

제공된 고정 소스에서 다음 경로가 남습니다.

| 공격·실패 시나리오 | 외부 authority만으로 해결되지 않는 부분 | 사용자가 보게 되는 실패 |
|---|---|---|
| worker를 재할당했지만 이전 worker가 계속 실행 | 완료 조건에 worker 세대 fencing이 없음 | 철회하거나 정정한 사실이 다시 나타남 |
| 호출자에게 scope tag를 강제 | 내부 background 작업은 scope 제한의 예외 | 다른 범위의 근거가 통합·reflect에 섞임 |
| directive를 API에서 제한 | untagged directive가 적용되는 별도 경로 존재 | 승인하지 않은 지시가 답변에 영향을 줌 |
| shared observation 옵션을 잘못 허용 | tag를 넘어 untagged 파생 observation 생성 | 프로젝트 간 사실이 오염됨 |
| 근거를 삭제하고 결과만 검사 | 내부 합성은 이미 삭제된 근거를 사용했을 수 있음 | 출처 없는 결론이 정상 답변처럼 전달됨 |
| tombstone을 같은 cluster의 다른 schema에 보관 | 전체 cluster나 과거 volume 복원은 그 기록도 되돌릴 수 있음 | 오래된 backup에서 삭제 자료 부활 |

단일 worker는 동시 실행 가능성을 줄이지만 crash·재시작·취소·관리자 복구 이후 살아 있는 이전 실행을 배제하지 못합니다. `replace`와 content hash도 같은 본문 중복에는 도움이 되지만 승인 revision·source generation·삭제 epoch의 유효성을 대신하지 않습니다.

이를 고치려면 retain의 여러 transaction, consolidation, refresh, import, 삭제 경로를 함께 수정해야 합니다. 현재 자료로 이를 “작은 extension”이나 “싼 fork”라고 부를 근거는 없습니다. 다만 제공된 조사에는 큰 모듈의 일부 미열람 범위도 있으므로, **전체 Hindsight 코드에 대한 완전 감사 결과로 확대하지는 않습니다.** [엔진 근거](research/local-first-engine-evidence.ko.md), [고정 Hindsight 소스](https://github.com/vectorize-io/hindsight/tree/a9eeed77f9bce99d8f97d39a30d3281747300824)

직접 엔진을 선택하면 기존 semantic 품질과 성숙한 연산을 잃을 위험이 있습니다. 이 비용은 작은 schema나 짧은 코드로 상쇄됐다고 주장할 수 없습니다. 아래 전체 의미 동작과 비교 평가를 구현 완료 조건으로 둡니다.

## 2. 모듈 경계와 전체 의미 엔진

제품의 권위는 deployment별 PG에 하나씩 둡니다. 회사·고객·개인 deployment는 같은 schema와 연산 의미를 사용하지만 corpus·credential·모델 경로·backup을 분리합니다.

| 모듈 | 소유 책임 |
|---|---|
| `domain` | identity, binding, command, 승인, revision, 유효성, 상태 전이 |
| `storage` | PG transaction, provenance graph, 권한 있는 조회, migration |
| `jobs` | durable queue, lease, fencing, retry, 취소, operation receipt |
| `engine` | extraction, consolidation, retrieval, reflect, correction |
| `model_gateway` | 목적별 승인 route, 입력 유효성 검사, inference admission, 비용 |
| `rules` | 정확한 세 범위, selector, 승인 revision, 충돌·전달 판단 |
| `api` | MCP와 adapter/admin API를 같은 domain handler에 연결 |
| `adapters` | Claude/Codex/omp event 변환, lineage, capture, context 전달 |
| `ops` | installer, supervisor, doctor, backup/restore, 삭제 journal |

**추출과 통합의 유일한 작업 소유자는 `jobs`를 사용하는 제품 worker입니다.** 모델 runtime은 추론 요청을 실행할 뿐 job의 성공·재시도·최종 publication을 선언하지 않습니다. MCP나 native hook도 별도 background queue를 만들지 않습니다.

전체 chain은 다음처럼 구현합니다.

1. **Capture와 ingest:** user/assistant/tool event를 구분하고 source span·digest·coverage·snapshot을 보존합니다. 원문 저장과 후속 job 등록을 한 PG transaction으로 commit합니다.
2. **Extraction:** 사실, codebase finding, preference, human correction, investigation, rule candidate를 구분합니다. claim에는 부정, 조건, 예외, 잠정성, 적용 시점과 근거 span을 남깁니다. schema 통과를 사실성 검증으로 취급하지 않습니다.
3. **Consolidation:** 같은 권한·적용 범위와 호환되는 snapshot의 claims만 묶습니다. 반복·모순·대체·조건부 관계를 표현하고 원래 근거를 유지합니다. 같은 run의 중복 export를 반복 조사 횟수로 세지 않습니다.
4. **Recall:** 권한과 유효성이 확인된 집합에서 vector와 lexical 검색을 결합합니다. code identifier는 lexical 경로를 유지합니다. provenance의 support/contradict/supersede 관계를 제한적으로 확장해 단순 top-k 이상의 근거 연결을 제공합니다.
5. **Reflect:** 선택한 evidence manifest를 가지고 질문별 합성을 실행합니다. 문장별 citation을 요구하고 존재하지 않는 출처·revision을 거절합니다. citation 존재 검사는 의미적 entailment의 완전한 증명이 아닙니다.
6. **Correction:** 정정은 새 evidence이며 기존 claim과 적용 조건별 관계를 가집니다. 영향을 받는 파생물을 무효화하고 필요한 재추출·재통합을 같은 queue로 실행합니다.
7. **다음 작업의 재사용:** 새 run에서 수정된 근거가 선택되는지 확인합니다. 로그를 저장했다는 이유만으로 학습 효과를 인정하지 않습니다.

파생물에는 lineage를 필수로 둡니다. 하나의 결론에 필요한 여러 전제는 모두 유효해야 합니다. 대체 근거가 있는 경우에는 그 대체 관계를 명시합니다. 이를 표현하지 못하면 근거 하나가 철회돼도 보수적으로 파생물을 숨깁니다.

주입한 memory, tool echo, 이전 reflect는 독립 human evidence로 다시 세지 않습니다. 모델이 만든 결론은 자동으로 승인 규칙이나 새로운 사실 권위가 되지 않습니다. [전체 loop 요구](research/local-first-invocation-contract.ko.md)

## 3. API·상태·동시성 계약

Agent-plane의 도구는 다음 네 개로 고정합니다. producer capture, 승인, publish, migration, backup은 별도 권한의 API/CLI입니다.

| 도구 | 의미 |
|---|---|
| `memory_context` | bounded recall, 또는 명시적인 reflect operation 요청 |
| `memory_inspect` | 선택한 item의 근거·유효성, operation의 진행 상태 조회 |
| `memory_record` | 모델 출처가 명시된 note/candidate 기록 |
| `memory_feedback` | 정정·거절·철회 요청 제출 |

모델 payload의 `human`, `approved`, `team` 같은 필드는 권한을 만들지 못합니다. 승인·공유 publication은 검증된 approver credential과 exact revision으로만 처리합니다.

Operation은 `accepted → queued → running → succeeded`를 기본으로 하고 `blocked`, `retry_wait`, `failed`, `cancel_requested`, `cancelled`, `superseded`를 구분합니다. 별도로 `semantic_ready`와 coverage를 표시합니다. 원문 ingest가 성공해도 추출이나 embedding이 끝나지 않았다면 검색 가능하다고 응답하지 않습니다.

주요 오류는 다음 의미를 갖습니다.

- `BINDING_REQUIRED`: 허용된 project binding을 확정하지 못함.
- `IDEMPOTENCY_CONFLICT`: 같은 key로 다른 payload 제출.
- `MODEL_ROUTE_BLOCKED`: 해당 목적의 승인 모델 경로 없음.
- `CAUSAL_NOT_READY`: 요구한 ingest/processing 지점에 도달하지 못함.
- `CONTEXT_STALE`: 선택 이후 출처·권한·policy가 바뀜.
- `TARGET_UNRESOLVED`: 보호 행동의 적용 조건을 판단할 정보 부족.
- `REQUIRED_CONTEXT_OVER_BUDGET`: 필수 본문을 안전하게 전달할 수 없음.
- `RESTORE_HEAD_UNVERIFIED`: 최신 삭제 기록을 확인하지 못함.

같은 `(principal, binding, command, idempotency_key)`와 같은 digest는 같은 effect와 operation ID를 돌려줍니다. **철회 후 replay가 예전 본문까지 그대로 돌려준다는 뜻은 아닙니다.** receipt ID는 유지하되 현재 유효성과 상태를 다시 검사합니다. MCP request ID·transport session은 이 key를 대신하지 않습니다.

권위 watermark는 commit 순서가 보장되도록 짧은 transaction 안에서 잠그는 clock row로 발급합니다. 단순 sequence 번호를 commit 완료 순서로 간주하지 않습니다. ingest head, processing coverage, operation별 materialization 상태도 구분합니다.

Worker publication transaction은 반드시 lease token, 예상 source generation, 현재 permission/policy epoch, 삭제 상태, 모델·parser/index generation을 검사합니다. 늦은 worker는 계산을 마쳤더라도 commit할 수 없습니다.

**모델 호출 전 fence도 필수입니다.** 추출·embedding·rerank·통합·reflect 모두 다음 절차를 따릅니다.

- 현재 권한과 source 유효성을 검사한 immutable input manifest 생성.
- model gateway의 admission에서 causal minimum과 현재 epoch 재검사.
- 추론 이후 publication과 전달 직전에 다시 검사.

로컬 구현에서는 gateway가 trust-domain별 shared advisory lock을 inference 동안 유지하고, 최종 철회 완료는 exclusive lock으로 기존 실행이 빠져나간 뒤 선언하는 보수적인 방식을 선택합니다. LLM을 기다리는 DB transaction은 열어 두지 않습니다. 철회 요청은 먼저 `revoking`을 commit해 새 admission을 막고, 기존 호출의 취소·timeout·종료를 기다립니다.

이 방식은 철회 완료 지연이라는 비용이 있습니다. 이미 provider로 전송된 내용을 회수한다고 주장하지 않으며, drain이 끝나지 않았다면 최종 `retracted` ack를 반환하지 않습니다. [호출·일관성 계약](research/local-first-invocation-contract.ko.md)

## 4. project·branch·fork·compaction과 세 host

권한은 operator가 등록한 deployment/project binding과 credential에서 결정합니다. CWD·remote URL·bank name은 binding 조회의 단서이며 권한 자체가 아닙니다. 미등록 workspace를 개인 global memory로 fallback하지 않습니다.

Identity는 다음을 별개로 보존합니다.

- deployment, trust domain, principal, project;
- repository incarnation, workspace/worktree, code snapshot;
- root-run, host thread, agent, turn, event, tool call.

Branch 이름만으로 현재 code truth를 판단하지 않습니다. commit과 dirty 파일 digest 등 실제 dependency가 맞아야 현재 사실로 전달합니다. 확인할 수 없으면 historical/unknown입니다. Git이 없는 프로젝트도 등록할 수 있으며, unborn repository의 identity를 첫 commit hash에 의존시키지 않습니다.

Repository fork는 기본적으로 별도 project binding입니다. 반면 session fork는 같은 project 안의 새 context lineage입니다. 상속한 대화는 새 독립 관측으로 세지 않습니다.

| Host | Adapter의 핵심 처리 | 실제 검증이 필요한 부분 |
|---|---|---|
| Claude | UserPromptSubmit recall, PreToolUse deny, agent ID 분리, compact/resume 재평가 | hook 실패 차단 설정, replay된 오래된 context |
| Codex | prompt hook, tool deny, agent/thread lineage, capability별 wrapper | fork 식별, trust hash, hosted tool 사각지대 |
| omp | `before_agent_start`, `context`, `tool_call`, `ctx.agent`별 상태 | 재진입 dedup, parent MCP proxy와 child 분리 |

omp의 module-global 변수와 공유 MCP 연결에 delivery 상태를 저장하지 않습니다. Codex의 parent session ID도 child identity로 사용하지 않습니다. fork·compact·resume에서는 새로운 context generation을 발급하고 delivery receipt를 재평가합니다. 이미 전달된 본문은 삭제할 수 없으므로 긴급 철회 때는 보호 행동을 중단하고 새 context로 전환할 수 있어야 합니다. [host 근거](research/local-first-host-evidence.ko.md)

일반 prompt도 workflow와 같은 handler를 사용합니다. session 시작에는 memory/rule 본문을 보내지 않습니다. 실제 prompt가 들어오면 등록된 binding 안에서 필요한 recall만 수행합니다. phase/path가 없으면 unknown을 유지합니다.

Python 구현 가능성은 이미 제공된 실측으로 충분히 뒷받침됩니다. **Python 3.12 + 공식 `mcp==2.3.0` 하나의 HTTP edge에서 modern store, legacy read, autodiscover read, modern read가 같은 합성 자료를 처리했습니다.** 따라서 TypeScript 서비스나 두 개의 semantic core를 만들 이유가 없습니다. 다만 native 세 host의 실제 HTTP/stdio 연결은 별도 acceptance입니다. SQLite probe는 PG 제품 증거로 재사용하지 않습니다. [Python feasibility와 실제 wire 관측 범위](research/local-first-python-mcp-feasibility.ko.md), [공식 SDK dual-era 설명](https://py.sdk.modelcontextprotocol.io/run/legacy-clients/)

## 5. 정확한 세 활성화 범위와 최소 context

새 요청을 기준으로 선택지는 정확히 다음 세 개입니다. frozen proposal의 이전 범위 구분은 수정합니다.

1. **이 로컬 프로젝트** — 이 설치와 project binding에 적용. Git commit이나 팀 배포를 요구하지 않습니다.
2. **내 프로젝트들** — 같은 principal·trust domain에서 승인한 project 집합에 적용.
3. **팀 또는 프로젝트 공유** — 구성된 팀/프로젝트 approver가 승인한 revision을 공유 대상으로 publication.

`내 프로젝트들`은 개인·회사·고객 경계를 합치는 뜻이 아닙니다. 대상 project-set revision을 승인에 포함하고 새 대상 추가는 명시적으로 확인합니다. 공유 권한이 미구성인 경우에도 세 번째 선택지를 표시하되 활성화 불가 사유를 보여줍니다.

Candidate의 반복 횟수나 confidence는 승인 권한이 아닙니다. cancel·미응답은 candidate만 보존합니다. 승인에는 본문, selector, 예외, 대상, required 여부의 exact digest를 결합합니다. 범위 문자열이 같아도 적용 대상이나 조건이 넓어지면 새 승인이 필요합니다.

규칙의 정본과 활성 ledger는 PG가 소유합니다. export bundle과 host delivery cache는 projection입니다. 개인 규칙을 자동으로 팀에 배포하지 않고, root `CLAUDE.md`/`AGENTS.md`에 본문·목록·bridge를 추가하지 않습니다. 전체 catalog를 eager skill이나 `.omp/rules`로 옮기는 방식도 선택하지 않습니다.

Required rule selector는 `true/false/unknown`으로 평가합니다. 보호 행동에 적용될 가능성이 있는데 path나 phase를 모르겠다면 unknown을 false로 처리해 통과시키지 않습니다. `TARGET_UNRESOLVED`로 차단하고 조건을 해소합니다.

첫 새 path에서 필요한 규칙이 발견되면 다음 순서를 사용합니다.

- 현재 행동 deny.
- 필요한 원문과 revision을 모델에 전달.
- 이후 모델 호출과 새 행동에서 target·policy generation을 다시 검사.

Context를 붙인 최초 Write를 그대로 allow하지 않습니다. 동시에 이 절차가 자연어 규칙의 준수를 증명하지도 않습니다. 검사가 가능한 제약은 lint/검증기에, 보안은 ACL·sandbox에 맡깁니다.

임의 Bash·외부 IDE writer는 정확한 target footprint를 모를 수 있습니다. 해당 행동을 required-rule 지원으로 선언하려면 제한된 실행 wrapper로 footprint를 확인하거나, 가능한 필수 집합을 전달해야 합니다. 둘 다 불가능하면 차단합니다. native hook만으로 모든 writer를 포괄했다고 표시하지 않습니다.

Optional memory부터 예산을 줄이고 required 본문은 자르지 않습니다. 부족하면 작업 분할이나 중단입니다. 실제 렌더링된 token과 bytes를 측정하고, rule ID/revision·context generation별로 중복 전달을 줄입니다. 서버 cache가 prompt token을 없앤다고 계산하지 않습니다.

규칙 충돌도 scope별 임의 우선순위로 덮어쓰지 않습니다. 구조화된 충돌은 차단하고, 자연어 충돌은 검토 대상으로 표시합니다. 예외·supersedes 관계에는 해당 규칙을 변경할 권한이 필요합니다.

## 6. 삭제·복원·보안의 완료 의미

`retracted`, `physically_purged`, `backup_retention_complete`를 별도 상태로 둡니다. 삭제 범위에는 raw, claims, observations, embeddings, reflect, cache, spool, jobs, exports, projections가 포함됩니다. 외부 provider retention이나 이미 전달한 transcript까지 삭제했다고 표시하지 않습니다.

복원 방어를 위해 **본문 없는 deletion journal을 PG backup과 별도로 유지**합니다. 이는 검색 엔진이나 두 번째 job queue가 아니라 복원 시 넘어서는 안 되는 삭제 floor입니다.

삭제 요청은 권한·idempotency 검증 후 journal intent를 fsync하고 PG에 반영합니다. 두 저장소 사이 crash는 journal을 기준으로 보수적으로 reconcile합니다. 최종 삭제 ack는 journal 내구성, 파생물 차단, 진행 중 inference drain을 확인한 뒤 반환합니다. journal에는 source identity·삭제 범위·operation 식별자만 남기고 삭제 본문을 복제하지 않습니다.

같은 disk의 별도 파일은 PG volume 복원에는 도움이 되지만 전체 장치 손실을 해결하지 않습니다. **현재 deletion head를 확보하지 못한 전체 복구는 `RESTORE_HEAD_UNVERIFIED`로 읽기를 닫습니다.** 과거 backup 안의 서명된 기록만으로 최신성을 증명할 수는 없습니다. 독립 보관 매체가 필요한 재해복구 보장은 실제 운영 조건으로 남깁니다.

Restore는 service 비공개 상태에서 schema 복구, 최신 삭제 floor 적용, source/derived reconciliation, 오래된 job generation 폐기, 검증 순으로 진행합니다. binary rollback과 schema rollback도 분리합니다.

보안 경계는 agent, producer, approver, operator, migration 권한을 나눕니다. loopback에도 인증·endpoint identity·Host/Origin 검증을 적용하고 DB/operator credential을 agent에게 주지 않습니다. 같은 UID는 credential과 승인 도구를 읽을 수 있으므로 개인 로컬 승인 UI를 강한 인간 인증으로 표현하지 않습니다. 공유 환경의 강한 승인은 별도 OS identity·관리 환경·IdP 같은 실제 경계가 필요합니다.

모델 경로는 목적별 manifest로 allowlist하고 개인 provider env를 상속하지 않습니다. 승인되지 않은 fallback, 자동 weight 다운로드, telemetry는 허용하지 않습니다. 승인 route가 없으면 추출·reflect를 blocked로 표시하고 full 제품 지원을 선언하지 않습니다. [보안·복구 기준](research/local-first-invocation-contract.ko.md), [기존 경계 관측](research/unified-memory-pipeline-proposal.ko.md)

## 7. 설치, OSS 선택, Agent Flow 실행 단계

서비스 언어는 Python 3.12 계열, MCP는 실측한 공식 2.3.0을 초기 lock 기준으로 삼습니다. 저장소는 PostgreSQL + pgvector + pg_trgm, job은 같은 PG를 사용합니다. Redis·Neo4j·object store·두 번째 generic memory engine은 기본 구성에 추가하지 않습니다.

설치 후보의 역할은 다음처럼 제한합니다.

| 영역 | 1라운드 결정 | 추가 근거가 필요한 부분 |
|---|---|---|
| Protocol | 공식 Python SDK 한 edge | 세 native host와 stdio 실측 |
| Memory engine | 제품이 전체 의미 chain 소유 | Hindsight와 동일 조건 품질·유지비 비교 |
| Search | PG hybrid + 제한된 provenance 확장 | 한국어·identifier 검색 평가 |
| Durable jobs | PG lease/fencing, 하나의 lifecycle | crash·lease 탈취·취소 race 검증 |
| SIE | 기본 dependency 채택 보류 | 실제 engine 경계·저장·삭제·local runtime·license |
| Model runtime | 승인된 실제 route를 gateway로 연결 | hardware, weight/runtime license, 한국어 품질 |
| Backup/security | PG 복구 + 독립 삭제 floor + 권한 분리 | 전체 장치 복구와 배포별 인증 |

현재 SIE 자료는 pinned MCP package가 `mcp>=1.9,<2`이고 configured `SIE_BASE_URL`을 호출한다는 것까지입니다. 이를 local full engine의 증거로 쓰지 않습니다. 반대로 새 OSS 조사를 받기 전에 SIE의 검색·구조화 연산 재사용 가능성까지 배제하지도 않습니다. 모델 weight와 runtime license 역시 이번 입력만으로 확정하지 않겠습니다. 이 항목은 실제 모델 milestone의 차단 조건입니다. [SIE 고정 MCP 문서](https://github.com/superlinked/sie/blob/c571e0a75d804cb6d49795a99cd03ea901307a69/packages/sie_mcp/README.md)

설치는 product-owned venv·config·volume·supervisor를 만들고 기존 global host 설정을 덮어쓰지 않습니다. Colima daemon이 꺼져 있다는 사실은 readiness 실패로 명시합니다. native host trust는 별도 실제 승인 절차이며 installer가 자동 승인하지 않습니다. uninstall은 데이터 보존이 기본입니다.

Agent Flow는 제공된 main HEAD `0ffba881a0c3f1c20f41359f205ef4e517ed5482`의 별도 checkout으로 실행합니다. `pyproject`의 0.3.15 표기를 released version으로 확대하지 않고 기존 global 0.3.14를 교체하지 않습니다.

Unborn repo에는 task-owned bootstrap만 명시적으로 commit해 isolated worktree의 기반을 만듭니다. 기존 untracked research는 그대로 보존하며 `git add .`로 포함하지 않습니다. 그 이후 **Agent Flow가 아래 구현 계획을 실제 실행하도록 설정하는 것이 delivery 범위**입니다.

| 단계 | 구현 결과 | 완료를 인정하는 증거 |
|---|---|---|
| M0 | 계약, dependency/route lock, task bootstrap, Agent Flow plan/config | 사용한 checkout·plan·binding 확인 |
| M1 | PG domain, ingest, operation, job fencing | 응답 유실 replay, crash 복구, 늦은 commit 거절 |
| M2 | 실제 모델 기반 extract→consolidate→recall→reflect | 합성 corpus의 근거·조건·모순·후속 사용 |
| M3 | correction, forget, purge, restore | 파생 철회, spool replay, 오래된 backup 부활 차단 |
| M4 | Python dual-era MCP | 양 era가 같은 PG effect·revision 조회 |
| M5 | 독립 Claude/Codex/omp adapter | 일반 prompt·workflow·child·compact·fork 수용 |
| M6 | Agent Flow consumer 연결 | 실제 계획 실행과 동일 memory 의미 확인 |
| M7 | 1~2주 trial와 평가 | 사용 기록·품질·비용·장애에 근거한 판단 |

M2는 fake 모델이나 SQLite로 통과시킬 수 없습니다. Agent Flow 없는 세 host 실행을 먼저 확인하고 같은 adapter를 Agent Flow에 연결합니다. core/runner/installer 변경은 기본 0줄입니다. 격리 reviewer에는 author memory·MCP·credential을 자동 상속하지 않습니다. clean HOME만으로 보안 격리를 증명하지도 않습니다.

## 8. 로컬 완료, 실사용 hard stop, cloud 계약

로컬 완료는 모든 모듈이 존재한다는 뜻이 아니라 다음 행동을 관측했다는 뜻입니다.

- 공개 합성 자료의 정정이 추출·통합·reflect를 거쳐 다른 host의 다음 작업에 반영됨.
- 응답 유실·cancel·재시작·동시 client에서도 effect 중복과 stale publication이 없음.
- 새로운 path의 required rule이 첫 보호 행동을 차단하고 재계획 전에 전달됨.
- compact·resume·fork·child에서 context와 capture 중복·누락을 구분함.
- 다른 project/customer와 승인되지 않은 model route를 거절함.
- source 철회가 모든 파생물에 반영되고 과거 restore·spool replay로 부활하지 않음.
- source docs의 capability와 설치 binary의 실제 동작을 따로 기록함.

1~2주 trial은 synthetic/public 개인 프로젝트부터 시작합니다. 날짜만 채우면 완료가 아닙니다. coding, review, 조사, 일반 질문에서 no-memory와 동일 조건 hybrid/RAG baseline을 함께 비교합니다.

측정에는 실제 후속 수정 성공률, 근거 오류, false promotion, candidate 거절, capture gap, blocked 작업, startup/turn/recall token, roundtrip, p50/p95 latency, 모델 비용, 저장·운영 시간이 포함됩니다. 의미 출력의 동일성을 deterministic 기준으로 요구하지 않고, API 상태·권한·revision·출처 불변식과 의미 품질 평가를 분리합니다.

다음은 trial hard stop입니다.

- 회사·고객 데이터의 잘못된 경계 접근 또는 미승인 반출.
- 철회 자료나 규칙의 부활.
- 지원한다고 선언한 보호 행동의 required-rule 우회.
- 탐지되지 않은 capture gap 또는 project/child identity 혼선.
- 승인 없는 규칙 활성화.
- 영구 실패·디스크 부족·queue 정체를 성공이나 빈 결과로 숨김.

발견 시 자동화를 중단하고 데이터를 보존한 채 원인을 수정합니다. recall-only나 reflect-off로 바꾼 상태를 full acceptance 통과로 기록하지 않습니다.

Cloud는 지금 provisioning하지 않습니다. local acceptance와 trial을 통과한 같은 artifact/schema/operation 의미에 개인 VM의 TLS·인증·backup·approved route를 추가합니다. 이전 대상은 명시적으로 선택한 개인 corpus뿐입니다. 회사 corpus를 개인 cloud에 옮기지 않으며 single VM을 HA로 표현하지 않습니다.

## 9. Peer가 공격해야 할 7개 쟁점과 선택을 바꿀 증거

다음 질문에 대한 반박을 2라운드에서 받고 싶습니다.

1. **직접 엔진의 범위가 실제로 좁은가?** 조건부 claim·모순·통합·근거 reflect·정정까지 소유하면 Hindsight fork보다 유지비가 커지는 지점은 어디인가?
2. **Inference 동안의 shared lock이 과도한가?** 철회 지연을 줄이면서 admission 전 fence와 최종 ack 의미를 유지할 더 단순한 계약이 있는가?
3. **PG와 삭제 journal의 crash 상태가 빠졌는가?** journal intent 이후 PG rollback·응답 유실·전체 장치 복원에서 효과와 receipt를 어떻게 오라클로 검증할 것인가?
4. **Unknown selector가 정상 workflow를 지나치게 막는가?** 임의 Bash와 phase 미상 작업에 대해 요구를 축소하지 않는 현실적인 지원 경계는 무엇인가?
5. **`내 프로젝트들`의 대상 관리가 사용자 의도에 맞는가?** 명시적 project-set revision보다 동적 등록을 허용해도 승인 확대와 고객 경계를 통제할 수 있는가?
6. **Lineage와 citation 검사가 의미 오류를 충분히 드러내는가?** 한국어 부정·예외·간접 정정과 대체 근거를 어떻게 평가해야 하는가?
7. **SIE나 다른 OSS가 소유 경계를 줄여 줄 수 있는가?** 동일 job lifecycle, 사전 scope 검사, stale commit 차단, 파생 철회·restore를 보존하는 구체적 재사용 단위는 무엇인가?

다음 새 증거는 선택을 바꿀 수 있습니다.

- Hindsight의 **모든** 내부 합성·publication·import 경로에 적용되는 upstream fencing/eligibility 계약과 실제 stale-worker·철회·restore 통과 결과.
- SIE 또는 다른 OSS의 전체 의미 chain, local 실행, provenance·purge·restore, license가 확인되고 제품의 단일 작업 소유권과 충돌하지 않는다는 근거.
- 같은 corpus·모델·예산에서 직접 엔진이 Hindsight의 후속 작업 품질을 달성하지 못하고, Hindsight의 필요한 통제를 유지 가능한 범위로 구현할 수 있다는 비교 결과.
- 설치된 세 host의 실제 기능이 문서 계약과 달라 현재 adapter/barrier로 정상 workflow를 지원할 수 없다는 runtime 관측.

**현재 선택은 직접 소유하는 단일 PG 의미 엔진입니다. 그 선택을 방어하는 기준은 코드 크기가 아니라 전체 semantic loop와 철회·승인 불변식을 실행 가능한 경계에서 검증할 수 있는가입니다.**

**같은 job을 두 queue가 소유하지 않는다.**
- amm의 `dispatch_retain`은 문서를 엔진에 넘기고 엔진의 terminal 상태를 확인하는 데까지만 소유한다.
- amm은 추출을 다시 실행하지 않는다. 재제출은 같은 `document_id`와 같은 content로만 한다. 엔진의 content_hash gate가 중복을 흡수한다(engine-evidence §1 Retain).
- amm job은 lease, fencing token, expected generation을 가진다. lease를 잃은 늦은 dispatcher의 commit은 거절한다.
- amm job 종류는 `dispatch_retain`, `dispatch_delete`, `rebuild_binding`, `restore_reconcile`, `retention_sweep`, `shared_rule_index`다.
- 엔진의 retain, consolidation, refresh에는 fencing이 없다. 그래서 §3 A3의 single-worker 조건에 의존한다.

**Event 상태:** `accepted → dispatched → engine_running → indexed → consolidated`, 또는 `failed_retryable | failed_permanent | blocked_route | superseded | retracted`.
- queryable은 `indexed`이면서 binding barrier가 꺼진 상태다.
- 엔진의 완료 표시는 data commit과 별도 txn이다(engine-evidence §1). 그래서 amm이 op 상태를 조회해 확인한 뒤에야 `indexed`로 둔다.

**읽기 envelope:**
- `status`: `ok | partial | unavailable | blocked | binding_required`
- `stamp`: `{binding, rule_set_digest, retraction_epoch, index_watermark, engine_pin, route_id, mode}`
- `coverage`: `{pending, consolidation_pending, capture_lag, excluded_reasons}`
- 각 item: `kind(rule|evidence|observation|reflect|candidate)`, `authority(approved|human_source|ai_derived|ai_consolidated|ai_reflect)`, `validity{branch, commit, historical}`, `citation`, `rev`

**오류:** `BINDING_REQUIRED`, `IDEMPOTENCY_CONFLICT`, `CONTEXT_STALE`, `RETRACTION_IN_PROGRESS`, `REQUIRED_CONTEXT_OVER_BUDGET`, `ROUTE_NOT_APPROVED`, `SERVICE_UNAVAILABLE`, `PERMISSION_DENIED`, `SCHEMA_UNSUPPORTED`. unavailable은 empty가 아니고 partial은 complete가 아니다.

**일관성이 뜻하는 범위**
- 같은 stamp에서 결정적으로 같아야 하는 것: rule 선택, binding 해석, 예산 절단(item 단위), 오류 분기, recall 후보. recall은 non-LLM retrieval+rerank라고 추정하지만 [미확정]이다.
- reflect와 추출은 LLM 출력이라 매번 같다고 약속하지 않는다. stamp로 차이의 출처를 설명할 수 있게만 한다.

## 4. Identity·lineage·호출 표면·context·세 범위 규칙

**Identity**
- deployment(trust domain)는 설치 때 고정한다.
- binding은 `realpath(git common-dir)`가 operator가 등록한 alias에 있을 때만 해석된다. 그렇지 않으면 `BINDING_REQUIRED`이고 default나 global bank로 넘어가지 않는다.
- worktree는 같은 binding이다. branch, HEAD, worktree path는 provenance로 남긴다.
- principal은 설치별 token으로 정한다. `clientInfo`, `serverInfo`, MCP session, JSON-RPC id는 identity나 key로 쓰지 않는다(F2, F11).
- root_run은 adapter가 host root session을 처음 볼 때 발급하는 UUID다. host session id는 속성으로만 둔다.
- agent_path 출처: Claude와 Codex는 `agent_id`, omp는 `ctx.agent` chain이다. omp에서 module-global 상태는 금지한다(F7).
- domain idempotency key는 `(root_run, host turn/event id, kind)`의 digest다.

**fork·compact·resume·child (F6, F7)**

| 사건 | Claude | Codex | omp | amm 처리 |
|---|---|---|---|---|
| compact | SessionStart `compact` | SessionStart `compact` | `session_compact` | ctx_gen 증가, 아직 적용되는 mandatory만 재전달(optional은 재전달 안 함) |
| resume | `resume`(주입한 text replay) | 미확인 | 미확인 | ctx_gen 유지, revision 재검사, 바뀐 rule만 supersede 원문 전달 |
| fork | `fork`(≥2.1.214) | hook 신호 없음 | switch/branch reason fork | 새 root_run(parent link)에 receipt 복사. Codex는 capability `none`이라 degraded로 표시 |
| child | fork가 아닌 subagent는 새 context | session_id가 parent 것 | MCP proxy 공유 | 빈 receipt 또는 복사. omp는 adapter API에 `ctx.agent`를 명시해 전달 |

**호출 표면**
- session을 시작할 때 memory·rule 본문은 0이다.
- MCP tool은 4개이고 instructions는 512자 이하다(F3, F10). 각 tool이 받는 인자는 다음과 같다.
  - `memory_context`: query, mode=recall|reflect, budget
  - `memory_inspect`: item_ref
  - `memory_record`: note 또는 candidate
  - `memory_feedback`: correct, reject, retract_request
- 모델 tool로는 human이나 approved 권위를 자가 선언할 수 없다. retract_request는 사람이 CLI나 host 권한 prompt로 확인해야 실행된다. 이것이 prompt injection을 통한 memory 삭제 공격을 막는다.
- capture, 승인, admin은 CLI와 adapter API로만 한다.

**Per-prompt hook(UPS, `before_agent_start`)이 주입하는 것**
- (a) 아직 전달되지 않은 `phase=any ∧ path=any` mandatory rule의 원문
- (b) optional recall. [제안] score 임계값 이상, 최대 3개, rendered 600 token 이하, 이번 ctx_gen에서 아직 전달하지 않은 것만
- 해당하는 것이 없으면 **0 bytes**다.
- 예산은 item 단위로 자른다. mandatory를 자르지 않고 `REQUIRED_CONTEXT_OVER_BUDGET`을 반환한다.
- 주입 block에는 receipt marker를 넣는다. capture는 이 block을 제외해 재귀적 capture를 막는다.
- Claude는 timeout이 나면 context를 버리고 prompt를 진행한다(F4). 이 경우 degraded로 기록한다.

**세 범위**
- **① 이 로컬 프로젝트**: deployment와 binding에 묶인다. amm DB에만 있고 Git이나 팀과 무관하다.
- **② 내 프로젝트들**: 같은 deployment와 principal의 모든 binding에 적용된다. 회사 배포의 "내 프로젝트"는 회사 배포 안에만 머문다.
- **③ 팀·프로젝트 공유**: repo의 비-eager 경로(`.agent-memory/rules/`)에 있는 파일이다. 기본 branch에 merge된 revision이 정본이고 PR 승인이 권위다. amm은 digest projection만 가진다. approver가 구성되지 않았으면 선택지는 남기고 사용 불가 사유를 표시한다.

제시할 때는 항상 이 세 옵션이다. 취소하거나 응답이 없으면 candidate로만 남는다. 승인은 body, selector, exception, target의 digest에 묶인다. 적용 조건을 넓히면 다시 승인받아야 한다. 같은 `rule_key`에서 ③은 기본적으로 override할 수 없다. 충돌은 활성화 시점에 표시한다.

**First-action barrier**
- Claude와 Codex는 PreToolUse, omp는 `tool_call`에서 Write, Edit, apply_patch의 대상 path를 계산한다.
- 아직 전달되지 않은 path rule이 있으면 **deny하고 사유에 rule id, rev, 원문을 담는다.** receipt를 기록한 뒤 재시도는 allow한다.
- allow+context 방식은 전달로 세지 않는다(F5).
- 다음은 coverage gap으로 표시한다: Bash, hosted tool, IDE, Codex fail-open. 검사 가능한 규칙은 lint와 CI로 집행한다.
- `.omp/rules`로 내보내지 않는다(F12). root `CLAUDE.md`와 `AGENTS.md`에는 쓰지 않는다.

## 5. 전체 semantic chain과 단계별 실패 가시성

| 단계 | 소유 | 실패 시 소비자가 보는 상태 |
|---|---|---|
| capture | host adapter → 0600 bounded spool → adapter API | `capture_lag`. spool이 넘쳐도 버리지 않고 `capture_gap`과 해당 구간 watermark를 기록 |
| durable ingest | amm: event와 outbox를 한 txn에 | `IDEMPOTENCY_CONFLICT`, `BINDING_REQUIRED`, `rejected_tombstoned` |
| signal 선택 | amm의 결정적 규칙(LLM 0) | 제외 사유를 coverage에 기록. 조용히 버리지 않음 |
| claim 추출·embedding | Hindsight retain | `blocked_route`, `failed_retryable` / `failed_permanent` |
| 통합 | Hindsight auto consolidation | `consolidation_pending` |
| recall | amm epoch gate → recall → authority·validity enrich | `unavailable`, `RETRACTION_IN_PROGRESS`, `partial` |
| reflect | 명시 mode에서만. `include_based_on=true`, 결과는 candidate | `CONTEXT_STALE`, 300s timeout |
| 정정·철회 | 사람 채널 → tombstone·barrier → delete, rebuild | ack 시점에 barrier on. 재구성 중에는 `unavailable` |
| 다음 작업 | hook, barrier, tool | delivery receipt |

- **사람의 정정**은 human_source event로 남는다. 거기서 추출된 fact의 권위는 ai_derived이며, 출처가 사람이라는 사실은 provenance로 함께 남는다. 정정이 특정 item의 오류를 가리키면 해당 source를 철회하고 barrier를 건다.
- **recurring investigation**은 서로 다른 root_run의 수로 센다. event 수로 세지 않는다.
- **거절한 candidate**는 `(rule_key, normalized digest)` 기준 rejection ledger로 재제안을 막는다. 새 근거가 있을 때만 다시 제안한다.
- **철회 중에도 rule plane은 독립적으로 동작한다.** 그래서 memory를 철회하는 동안에도 보호 대상 행동의 mandatory 규칙은 계속 전달된다.

| M1 | store, outbox, journal | **실제 PG**에서: 같은 key와 digest면 같은 receipt, digest가 다르면 conflict, 늦은 lease commit 거절, journal-PG 사이 crash 후 복구 |

- reviewer는 `AMM_MODE=off`로 돌리고 memory MCP를 상속받지 않는다. role별 env 지원 여부는 [미확정]이다.

## 7. 1–2주 trial hardstop과 cloud 계약

**순서**
- 0–2일: public·synthetic 자료만 쓴다.
- 이후: 개인 project를 쓴다.
- 회사 자료는 이번 trial 범위가 아니다. 별도 route 승인 뒤에만 다룬다.

매일 `amm doctor`와 `trial report`로 다음을 기록한다.
- startup과 turn당 rendered token, 추가 왕복 수, p50/p95 latency
- 승인·거절·false promotion, 중복·누락·blocked
- 철회 재구성 시간과 비용
- 후속 수정의 품질
- 운영에 든 시간

**즉시 중단하는 경우**
- binding이나 trust domain을 넘어 노출됨
- ack 이후 철회한 내용이 반환됨
- degraded 표시 없이 hook 경로에서 mandatory 규칙이 우회됨
- 승인되지 않은 egress가 관측됨
- watermark 불일치가 상태 표시 없이 발생함
- root 파일이 변경됨
- 선언한 RPO를 넘는 손실
- 중복 효과 발생

날짜만 채웠다고 통과로 보지 않는다.

**Cloud 진입 조건**
- local acceptance M1–M7과 hardstop 0건
- 같은 image digest, schema, policy
- 같은 단일 VM 구성에 TLS proxy와 SDK의 `token_verifier`/`AuthSettings`를 더하고, 암호화된 offsite backup과 개인 route를 둔다.
- legacy client는 sticky routing이 필요하다고 명시한다.
- 개인 corpus만 export/import하고 deletion head를 검증한다. **회사 corpus는 옮기지 않는다.**
- 지금 cloud를 provisioning하지 않는다.

## 8. 불확실성, peer가 공격할 질문, 선택을 바꿀 증거

**남은 불확실성:** 다음은 아직 확인하지 못했다.
- L9924 이후 reflect·refresh 코드
- recall이 observation의 based_on을 반환하는지
- tag 필터에 OR, 즉 "현재 branch ∨ 기본 branch ∨ branch 중립"이 가능한지
- trace를 끌 수 있는지
- Hindsight license
- 다국어 reranker 지원
- 설치된 host binary의 실제 negotiate 결과
- Codex fork 신호와 UPS replay

SIE는 round2 증거를 기다린다. pinned SIE MCP 패키지는 `mcp<2`라 edge로 쓰지 않는다. 다음 조건을 모두 만족할 때만 embedding·rerank의 HTTP 런타임 후보로 둔다.
- localhost에서 오프라인으로 동작한다.
- license 조건을 만족한다.
- Hindsight가 fork 없이 provider 설정으로 호출할 수 있다.

원격 `SIE_BASE_URL`은 egress로 취급한다.

**Peer 질문**
1. 문서를 delete하거나 invalidate하면 파생 observation과 mental model이 동기적으로 정리되는가? 그렇다면 binding 전체 재구성은 과잉 설계인가?
2. bank를 1:1로 나누면 internal background와 shared observation 예외가 정말 완전히 닫히는가? bank 안의 consolidation이 branch tag batch를 넘나드는 경로가 있는가?
3. coarse barrier로 생기는 가용성 손실이 normal prompt workflow에서 수용 가능한가? 아니면 처음부터 좁은 engine이 더 싼가?
4. PreToolUse deny 사유에 규칙 원문을 담는 방식이 Codex와 omp에서도 모델에게 그대로 보이는가? 길이 제한은 얼마인가?
5. per-prompt optional recall이 "의미 없는 context"인가? agent가 직접 호출하는 방식만 남겨야 하는가?
6. cluster 밖 deletion journal은 "단일 PG 권위" 원칙을 깨는가? 대안이 있는가?
7. amm의 결정적 signal 선택이 추출 품질을 떨어뜨리는가?
8. retract_request에 사람 확인을 요구하면 정정 루프가 너무 느려지는가?

**선택을 바꿀 증거**
- **좁은 PG engine 쪽으로 바꿀 증거**
  - 철회 재구성 시간이나 비용이 §3 trigger를 넘는다.
  - 한국어 eval이 baseline보다 낮다.
  - trace나 purge를 pin 고정 SQL 없이는 처리할 수 없다.
  - license나 오프라인 조건을 맞출 수 없다.
  - pin을 올리면 계약이 깨진다.
- **Hindsight 유지를 강화할 증거:** 동기적 파생 정리와 완전한 lineage가 source로 확인되면 barrier를 가볍게 줄인다.
- **queue 쪽:** lease와 fencing을 갖춘 PG 기반 job OSS가 확인되면 자체 outbox 대신 그것을 채택한다.
- **edge 쪽:** 설치된 host가 dual-era edge에 실패하면 같은 core 앞에 stdio shim만 추가한다.

이 문서의 모든 내용은 설계 판단이다. 구현, 테스트, native hook, 제품 동작은 아직 입증되지 않았다.

## 3. SIE 항목별 판정

**3.1 SDK import, 버전, 고정, wire [근거]**
- v1 `FastMCP(stateless_http=True)`를 사용합니다(S2 L14, L110-114). lock은 1.28.1입니다.
- SDK 2.x에서 막히는 지점은 두 가지입니다.
  - P1: import 자체가 실패합니다.
  - P4/whats-new: `stateless_http`, `transport_security`, `host`가 생성자에서 app builder/run으로 옮겨졌습니다.
- 따라서 pin만 올리는 업그레이드는 불가능합니다. `stateless_http=True`는 v1 legacy 경로의 옵션일 뿐이고, 2026-07-28 wire를 지원한다는 증거가 아닙니다.
- SIE 자체의 2026 wire 지원: 증거 없음 [미확정·현재 코드로는 불가 INFERENCE].

**3.2 localhost 기본값, HTTP/stdio**
- CLI 기본 bind는 0.0.0.0이고 Docker도 같습니다(S4 L32, S13). README의 local edge 예시만 `--host 127.0.0.1`을 명시합니다.
- cluster 기본값은 `http://localhost:8080`이지만 원격 URL로 바꿀 수 있고, http 평문도 거부하지 않습니다(S6 L11, L224).
- stdio 실행 경로는 없습니다.
- 'localhost MCP'라고 해서 처리가 로컬이라는 뜻은 아닙니다. edge는 문서 전체를 `SIE_BASE_URL`로 보냅니다(S2 L76, S8).
- HEAD 커밋 메시지에 따르면 SIE Cloud는 'SIE Relay(partner capacity)'로 요청을 넘길 수 있습니다. egress 체인이 설정한 gateway 너머로 이어질 수 있다는 뜻입니다 [근거: c571e0a 메시지 / 적용 범위는 INFERENCE].

**3.3 프로세스 수명주기**
- 단일 uvicorn 프로세스(factory)이고 `--reload`는 개발용입니다. supervisor는 없습니다.
- `/healthz`는 인증 없이 항상 ok를 반환하므로 readiness를 구분하지 못합니다.
- OAuth code store는 메모리에만 있어 재시작하면 사라지고 단일 worker 전제입니다(S7 docstring).
- 중요: v1 stateless에서는 lifespan이 요청마다 실행됩니다(P7). SIE docstring의 'process당 1회'와 다르게 요청마다 `MCPConfig.from_env()`와 `SIEAsyncClient` 생성·close가 일어납니다 [source-traced, 미실행].
- SDK v2에서는 session manager가 lifespan을 소유합니다(P3 docstring, PY lifespan story). 우리 PG pool은 v2 기준으로 smoke 확인이 필요합니다.

**3.4 ingress 인증, Host/Origin/CORS/OAuth**
- 인증은 정적 shared secret 맵(env CSV `secret:user`)이고, Bearer 접두어 없는 raw token도 받습니다(S5).
- anonymous는 fail-closed입니다(L229, L133). 이 부분은 좋습니다.
- DNS-rebinding 보호는 allowlist가 비면 꺼집니다(S2 L106). loopback에 bind해도 마찬가지입니다.
- CORS middleware는 없습니다(PR #305 sweep으로 확인).
- OAuth bridge가 기본으로 켜져 있습니다(L270).
  - /register, /authorize, /token은 인증 없이 열려 있습니다(L25).
  - access token이 곧 정적 connector secret이라 만료, audience, 개별 폐기가 없습니다(S7 L169, L334).
  - 공개 origin은 PUBLIC_URL로 고정하거나 loopback/allowlist에서만 파생합니다(#275 → #292/#305 수정).
- 인증된 identity(`state.user_id`)가 tool 동작에 쓰이지 않습니다. memory 도메인이라면 scope 누출로 이어집니다 [INFERENCE].

**3.5 env 정리 vs credential 전달**
- edge 프로세스가 cluster key(`SIE_API_KEY`)와 client secret 맵을 모두 env로 읽습니다.
- plugin-pack은 secret 인자를 받아도 버립니다(L65). 이 부분은 좋습니다.
- 그러나 생성되는 가이드의 `claude mcp add --scope user … --header "Authorization: Bearer ${…}"`는 shell이 값을 먼저 펼치기 때문에 **실제 secret 문자열이 `~/.claude.json` user scope(모든 프로젝트)에 평문으로 저장**됩니다 [INFERENCE: shell 확장 + X4 L533-535, L604, L708].
- 같은 가이드가 `~/.claude/skills` 전역 복사를 안내하는데, 우리의 3-scope 원칙 및 global eager 금지와 충돌합니다.
- 참고 사항:
  - SDK v2 client stdio는 자식 프로세스에 최소 allow-list env(`HOME/LOGNAME/PATH/SHELL/TERM/USER`)와 `env=`만 넘깁니다(P5). 이는 SDK client의 동작이며 host마다 정책이 다릅니다.
  - Claude `headersHelper`는 repo/plugin이 제공한 경우 credential 변수를 제거하고, trust를 받은 뒤에만 실행합니다(X4 ≈L1029-1044).

**3.6 작은 카탈로그, tool search, offload 결과, 로그, egress**
- tool 8개가 긴 docstring(Args 포함)과 함께 항상 노출됩니다. deferred loading이나 tool search는 없습니다.
- protocol이 stateless여도 tools/list 카탈로그의 렌더링 토큰은 매번 듭니다. SDK caching hint는 `ttl_ms=0`이고 override hook이 아직 구현되지 않았습니다(P6 caching README). 따라서 카탈로그 비용은 host별 실측 대상입니다 [실측 없음].
- 결과 구성에서 좋은 점:
  - artifact와 metadata를 분리합니다.
  - 추정값(`*_estimate`, `estimated: True`)과 커밋된 측정값을 섞지 않습니다(S9).
  - 원문 PII map을 돌려주지 않습니다(S8 L392).
  - 입력 bytes/chars/질문 수/chunk 수에 상한이 있습니다(S6, S8).
  - QA가 사용한 passage를 함께 반환합니다(S11).
- 나쁜 점: 구조화 출력의 사후 검증이 fail-open입니다(S10).
- 로그:
  - base URL을 INFO로 남깁니다(URL userinfo에 credential이 있으면 그대로 노출됨, INFERENCE).
  - oauth.py에는 로그 호출이 없습니다(#275 보고자가 확인).
  - OCR 실패 시 `exc_info` warning을 남깁니다.
  - uvicorn access log는 path, status, IP를 기록합니다.

## 4. SIE 외 공식·유지 modern 예시 (2–4개 + 상태)

1. **PY dual_era**(server.py, README)
   - 하나의 factory가 두 era를 서빙합니다. era 분기 키는 `ctx.request_context.protocol_version`이고 `MODERN_PROTOCOL_VERSIONS`와 비교합니다.
   - README caveat 1: HTTP era 분기는 현재 header만 봅니다. `MCP-Protocol-Version` 헤더가 빠진 2026 client는 legacy로 잘못 라우팅됩니다.
   - README caveat 2: 'bare stdio 실행은 legacy만 동작'한다고 적혀 있습니다. 반면 protocol-versions.md는 stdio에서도 server/discover를 받는다고 해서 **문서 간 모순**입니다. 결론: [미확정, stdio 미시험].
   - 판정: **채택(edge 기본형)**.
2. **PY bearer_auth**(`TokenVerifier`→`AccessToken(subject, scopes, resource)`, `AuthSettings(validate_token_resource=True)`, `get_access_token()`)
   - per-install token 검증과 principal 전달에 씁니다.
   - 판정: **채택**. 예시가 쓰는 `NO_DNS_REBIND`는 하네스 전용이라 복사하지 않습니다.
3. **PY middleware + lifespan**
   - `MCPServer.middleware`로 method만 감사 로그에 남기고(payload는 남기지 않음), binding을 확인할 수 없으면 거부합니다.
   - `MCPServer[AppState](lifespan=…)`로 DB pool을 보유합니다.
   - 판정: **채택**.
4. **PY 운영 문서**(deploy/asgi/legacy-clients)
   - loopback 기본 보호, 실제 hostname에서는 421, CORS 규칙, `stateless_http`는 legacy 전용(back-channel이 없어짐), 다중 worker에는 `RequestStateSecurity(keys)`와 같은 server name 필요, legacy session은 메모리 저장이라 sticky가 필요합니다.
   - 판정: **채택(운영 계약)**.

참고 또는 기각:
- **PY `mcpserver/memory.py`**: OpenAI embedding/LLM으로 egress가 발생하고, `postgres:postgres` DSN이 하드코딩되어 있으며, `~/.mcp/$USER`에 씁니다. → **기각**.
- **FastMCP 4.1**: 의존성 메타데이터와 문서만 확인했습니다. → **채택 안 함**(공식 SDK에 레이어만 하나 더 생기고 Prefect 의존성이 늘어남). 2026 wire 지원은 '거짓'이 아니라 **미확정**입니다.
  - 다만 Hindsight가 `fastmcp>=3.2.0`을 상한 없이 쓰므로(engine evidence L61), 새로 resolve하면 4.x(mcp 2.x)가 들어와 동작이 달라질 위험이 있습니다. lock으로 고정하거나 Hindsight native MCP를 외부에 노출하지 않아야 합니다 [INFERENCE, 미시험].
- **TS SDK v2**: 참고만 합니다. client 기본이 legacy라서, TS 기반 host는 opt-in하지 않으면 2025 handshake로 붙을 수 있습니다 [INFERENCE: host별 설정은 미확정]. 그래서 우리 서버는 legacy 서빙이 필수입니다.
- **Cloudflare createMcpHandler**: Workers(cloud) 런타임이라 지금 local 기반으로는 **기각**합니다. 원칙만 참고합니다: 인증된 handle 뒤에 저장, token을 로그·반환하지 않음, CORS는 인증이 아님.

- 라이브러리 major(mcp 2, FastMCP 4)와 protocol date는 서로 다른 축입니다.
- protocol의 statelessness(initialize/session이 없음)와 app의 상태(DB는 지속됨)는 다릅니다.
- startup handshake가 사라진 것과 prompt token 비용(카탈로그, 응답)은 별개입니다.

## 6. Reuse map (→ 우리 모듈, contract §2/§5/§6 기준)

- **edge app**(memory_context/inspect/record/feedback)
  - 출발점: PY dual_era + lifespan.
  - 구성: `MCPServer(…, subscriptions=False if unused)`. `streamable_http_app(host="127.0.0.1", max_request_body_size=명시, transport_security=None→loopback 자동 보호)`. 출력은 Pydantic.
  - SIE app.py에서는 factory/`/healthz` 형태만 참고하되, `/readyz`(DB·worker·watermark)를 따로 둡니다.
- **edge.auth**
  - PY bearer_auth의 `TokenVerifier`를 씁니다. per-install token은 Keychain이나 0600 파일에 두고 `hmac.compare_digest`로 비교합니다. principal은 binding/scope로 매핑해 domain에서 강제합니다.
  - SIE auth.py에서는 pure-ASGI 방식과 RFC 9110 Host 파서 아이디어만 참고합니다(Host를 어딘가에 반영할 때만 필요).
  - raw token 허용과 shared secret CSV는 기각합니다.
- **edge.policy**
  - PY middleware를 씁니다: method와 결과 코드만 감사 로그에 남기고, binding을 알 수 없을 때 required 동작은 거부합니다.
  - protocol_version은 진단용으로만 쓰고 identity로 쓰지 않습니다.
- **service.config**
  - SIE config.py의 frozen dataclass, fail-closed, clamp를 적응해 씁니다.
  - 기본값을 바꿉니다: loopback, OAuth off, 모든 route allowlist 명시, 원격 http 거부.
- **service.result_composer / budget**
  - SIE savings/offload에서 추정·측정 분리 표기와 입력·출력 상한을 가져옵니다.
  - qa의 '사용한 근거 반환'은 citation ID와 provenance 반환으로 적응합니다.
  - redact의 'raw 원문을 반환하지 않음' 원칙을 따릅니다.
  - transient 검색 의미론은 기각합니다(우리는 durable).
- **extract/reflect 검증**: SIE structured의 사전 subset 검사와 사후 jsonschema 검증을 쓰되, 반드시 **fail-closed**로 바꿉니다.
- **capture ingest**: MCP tool 인자로 받지 않습니다(4 MiB 제한, 권한 분리). hook에서 로컬 ingest API/CLI로 보냅니다.
- **installer/doctor**
  - SIE plugin_pack에서 'secret을 산출물에 쓰지 않음'과 URL normalize를 가져옵니다.
  - 등록은 local/project scope + `headersHelper`(Keychain) 또는 `${VAR}`로 합니다.
  - user-scope `--header` 리터럴과 `~/.claude/skills` 전역 복사는 기각합니다.
  - doctor는 era, protocol, Host 보호 상태, body 한도를 표시합니다.
- **나중의 개인 cloud**
  - PY deploy(정확한 allowlist, proxy-headers, RequestStateSecurity), 진짜 AS + `AuthSettings`를 씁니다.
  - SIE oauth의 하드닝 항목(S256-only, 정확한 redirect, 고정 PUBLIC_URL, X-Forwarded-* 무시)만 참고합니다.
  - '정적 secret을 access token으로 쓰는' bridge는 기각합니다.

## 7. 가장 강한 위험

1. **비호환**: SIE를 SDK 2로 옮기려면 사실상 재작성이 필요합니다(P1/P4).
   - SIE를 fork해도 문서 offload 도메인과 v1 배선만 남습니다.
   - stdio 2026 경로는 문서가 서로 모순되어 [미확정]입니다.
   - 2026 client라도 헤더를 빠뜨리면 legacy로 잘못 라우팅됩니다(dual_era caveat).
2. **로컬 노출**: SIE 기본값(0.0.0.0, 보호 off, OAuth on, 인증 없는 bootstrap route)을 회사 장비에서 그대로 쓰면 LAN에 노출됩니다. 정적 secret 하나가 유일한 방어선이 됩니다.
3. **같은 UID 한계**
   - SDK 기본 보호는 브라우저 DNS-rebinding만 막습니다. Origin이 없으면 통과하므로(P2 L75), 로컬의 비브라우저 프로세스는 bearer token 없이는 막을 수 없습니다.
   - 반대로 같은 UID 프로세스는 token 파일이나 Keychain에 접근할 수 있으므로 loopback 인증이 같은 UID 격리가 되지는 않습니다(기존 결론과 일치).
4. **Host wildcard prefix 비교**(P2 L66)
   - SIE PR #305가 1.28.1에서 보고한 패턴(`host:443@evil`)과 같은 비교가 2.3에도 남아 있습니다.
   - 브라우저 rebinding 방어에는 영향이 작습니다 [INFERENCE]. 다만 Host 값을 OAuth metadata나 링크에 반영하면 안 되고, allowlist는 정확한 값으로 씁니다.
5. **수명주기**: v1 stateless는 lifespan을 요청마다 실행합니다(P7). v2는 lifespan이 process 범위이며, PG pool·worker는 edge 밖 service가 소유해야 합니다(contract §5).
6. **egress**
   - edge가 로컬이어도 처리 경로는 원격일 수 있습니다(S2/S8, SIE Relay).
   - 우리 쪽에서는 Hindsight/LLM route allowlist를 시작 시점에 검증하고, 승인되지 않은 route는 fail-closed로 막아야 합니다.
7. **credential 누출**
   - 설치 가이드 패턴 때문에 `~/.claude.json`에 평문 secret이 남고, user scope라 회사·개인 프로젝트가 섞입니다.
   - URL userinfo가 INFO 로그로 남을 수 있습니다.
   - SDK가 잘못된 Host/Origin 값을 WARNING에 그대로 기록합니다(log injection).
8. **정확성**
   - 구조화 출력 검증이 fail-open입니다(S10).
   - dict 반환 시 structured_content가 비는 문제가 parent smoke에서 관찰됐습니다. Pydantic 출력이 필수입니다.
9. **context 비용**: 카탈로그 캐싱은 미구현이고 host 출력 상한은 25k tokens입니다(X4). 응답 예산은 host별 실측 토큰 기준으로 관리해야 합니다.
10. **공급망과 라이선스**
   - fastmcp 상한이 없어 4.x drift 위험이 있습니다.
   - TS SDK는 MIT/Apache 혼합입니다.
   - SIE 코드를 복사하면 Apache-2.0 §4에 따라 고지와 변경 표시를 해야 합니다(NOTICE 파일은 없음).

## 8. 미확정 사항과 parent smoke 후보 (실행하지 않음)

- SDK 2.3 stdio dual-era: `run_stdio_async` + `Client(StdioServerParameters, mode=auto/2026)`.
- non-default `transport_security`의 421/403 동작. Origin이 없을 때 통과하는지.
- body 4 MiB 초과 시 413.
- `TokenVerifier`에서 401과 PRM 응답.
- lifespan이 process당 한 번만 실행되는지(요청 N회 동안 pool이 하나인지).
- `subscriptions=False`일 때 listen 응답.
- 헤더 없는 2026 요청이 legacy로 잘못 라우팅되는지.
- FastMCP 4 소스 경로 검증.
- Hindsight가 fastmcp 4.x에서 동작하는지.

# Local-first 나머지 구성요소 OSS 조사 (2026-10-12)

**표기:** [근거]는 고정 source나 공식 문서를 직접 읽은 것, [추론]은 근거에서 도출한 것, [제안]은 설계 계약(구현 아님), [미확정]은 아직 확인하지 못한 것입니다.

**상태와 범위**
- 전부 source-only입니다. 설치, 빌드, 테스트, 로그인, cloud 호출은 0건입니다.
- 실행 근거는 parent의 SDK 2.3 probe 하나뿐입니다(SDK/HTTP/SQLite 범위). 제품, Hindsight, PG, native host를 증명하지 않습니다.
- GitHub 비인증 API가 rate-limit(403)에 걸렸습니다. 그 뒤의 pin은 `commits/<branch>.atom`의 최신 commit이고, HF 모델은 API `sha`입니다.
- 범주별로 대표 2~4개를 비교했습니다. 전체 Internet을 감사한 것은 아닙니다.
- CueFinder/codegraph 안은 제외했습니다. 아래 SQLite 비교는 일반 backend 비교입니다.

## 0. 결론
1. **DB:** 첫 local release와 이후 개인 cloud 모두 **PostgreSQL 18 + pgvector ≥0.8.7**을 단일 권위로 둡니다. SQLite는 host 쪽 임시 spool(표준 sqlite3, extension 없음)에만 씁니다.
2. **한국어 lexical:** extension 없이 app에서 토큰을 만들어 `array_to_tsvector` + GIN으로 색인합니다. 토큰은 kiwipiepy 형태소, 한글 음절 bigram, 코드 식별자 분해입니다. 품질 gate를 통과하지 못하면 2순위로 pg_bigm을 씁니다. PGroonga와 ParadeDB는 지금은 쓰지 않습니다.
3. **job:** 자체 최소 outbox에 lease와 fencing token을 둡니다. 검토한 OSS 큐는 완료나 heartbeat를 job id로만 갱신하므로 fencing 권위가 없습니다.
4. **migration:** Alembic, `pg_advisory_xact_lock`, migrator role, forward-only로 운영합니다. 앱 시작 시 자동 migration은 금지합니다.
5. **모델:** runtime은 llama.cpp `llama-server`입니다. embedding은 bge-m3, reranker는 bge-reranker-v2-m3입니다. 생성/추출 LLM 후보는 Qwen3.5-9B(Apache-2.0)입니다. 단, 회사 승인 route가 생기기 전까지 extraction/reflect는 `blocked`입니다. 개인 API나 기본값 fallback은 두지 않습니다. Team 구독은 새 background LLM 사용의 승인이 아닙니다.
6. **backup:** `pg_dump -Fc`를 age로 암호화합니다. 필요하면 pgBackRest ≥2.59.3으로 PITR을 더합니다. tombstone ledger는 restore 단위 밖에 두고 restore barrier를 거칩니다.
7. **배포:** macOS native(launchd + Homebrew 또는 Postgres.app)로 하고 Docker Desktop에 의존하지 않습니다. 접속은 loopback, SDK의 Host/Origin 자동 보호, 설치별 token으로 받습니다.

## 2. PG+pgvector vs SQLite+FTS5/sqlite-vec
| 축 | PG 18 + pgvector | SQLite + FTS5 + sqlite-vec |
|---|---|---|
| 동시성 | MVCC, row lock, `SKIP LOCKED`, advisory lock, LISTEN/NOTIFY | WAL에서도 writer는 한 번에 하나, `SQLITE_BUSY` 가능, checkpoint starvation 가능. MCP 프로세스 여러 개 + worker + admin이 경합 |
| vector | exact가 기본이고 HNSW, halfvec, sparsevec 지원. 보안 수정이 계속 나옴 | pre-v1 alpha. 저장소에 diskann/ivf 파일이 있어 ANN은 실험 단계로 보임[추론] |
| lexical(한국어) | core FTS에는 한국어 설정 없음. pg_trgm은 비알파벳 언어 미지원. app 토큰화로 해결 가능 | trigram은 2음절 단어(예: '결정', '철회')를 놓침(L842). app 토큰화가 필요한 점은 같음 |
| 권한·격리 | role, GRANT, RLS | 파일 권한뿐 |
| backup·restore | pg_dump, PITR, pgBackRest | `.backup`/`VACUUM INTO`. PITR는 별도 도구 필요 |
| Hindsight 호환 | 필수 조건(PG 14 이상) | 불가. SQLite를 고르면 narrow core만 남음 |
| Python | asyncpg | stdlib로 되지만 macOS 기본 Python은 extension 로드 불가 |
| local과 cloud 동일 core | 같은 PG major·extension 버전을 VM에 그대로 올릴 수 있음 | 단일 disk VM은 가능하나 동시성 모델이 다름 |

**판정:** PG로 갑니다. SQLite는 host spool에만 씁니다. 이것은 event_id 기준 replay 버퍼일 뿐 권위가 아닙니다.

**저장 용량 산수 [추론, 측정 안 함]**
- halfvec(1024)는 행당 2,056 bytes입니다. 10만 chunk면 약 206MB(tuple·index 제외)입니다.
- vector(1024)는 4,104 bytes, 10만 chunk면 약 410MB입니다.
- exact 검색 한 번은 약 1.0e8 곱셈-덧셈입니다. 지연 시간은 측정하지 않았습니다.
- 원칙: scope 필터 안에서 exact로 시작하고, p95가 예산을 넘을 때 HNSW와 `iterative_scan=strict_order`를 켭니다.

**locale [근거: [locale](https://www.postgresql.org/docs/18/locale.html) L126-133]**
- `initdb --locale-provider=builtin --builtin-locale=C.UTF-8`(PG17+)을 씁니다. 문자 분류는 Unicode 기반이고 정렬은 codepoint입니다.
- 기대 효과는 macOS와 Linux의 동작 일치이고, libc 정렬 규칙 변화로 인한 index 위험을 피하는 것입니다[추론].
- Hangul이 분류 단계에서 어떻게 처리되는지와 Hindsight와의 호환은 [미확정]입니다.

## 3. 한국어·식별자 lexical 계약 [제안]
- **정규화:** NFKC를 적용하고 ASCII만 소문자로 바꿉니다.
- **토큰:** Kiwi 형태소(체언·용언 어간), 한글 음절 bigram, camel/snake 식별자 분해, 원문 ASCII 단어의 합집합입니다. 이를 `array_to_tsvector(text[])`로 저장하고 GIN으로 색인합니다. core PG만 쓰므로 Cloud SQL에도 그대로 이식됩니다.
- **정확 식별자:** btree `=`와 ASCII용 pg_trgm을 씁니다.
- **manifest:** 행마다 `tokenizer_rev`를 기록합니다. 버전이 바뀌면 새 revision으로 재색인하고, 서로 다른 manifest를 섞어서 질의하지 않습니다.
- **순위:** ts_rank_cd는 BM25가 아닙니다. 그렇게 부르지 않습니다.
- **fusion:** amm이 RRF로 합칩니다. lexical, amm vector(선택), Hindsight recall을 각각 하나의 arm으로 보고 arm별 status를 반환합니다. 예: `unavailable≠empty`.

## 4. Durable job: 홍보 문구 vs 실제 보장

### Procrastinate
- **claim:** `FOR UPDATE OF jobs SKIP LOCKED` 후 `doing`과 worker_id를 기록합니다(L210-262).
- **heartbeat:** workers table에 기록합니다. 기본 간격 10s, stalled 판정 30s입니다.
- **stalled 재시도:** 사용자가 만든 periodic task가 `get_stalled_jobs`를 돌려야 합니다. `nb_seconds` 방식은 "may lead to wrongly retrying jobs that are still running"이라는 이유로 deprecated입니다([docs](https://github.com/procrastinate-org/procrastinate/blob/8279a61789fdf8227d6f513ad15e4b26f1b78b49/docs/howto/production/retry_stalled_jobs.md)).
- **finish:** `WHERE id=job_id AND status IN('todo','doing')`만 검사합니다(L276, L285). worker나 세대는 보지 않으므로 재시도 후 되살아난 stale worker도 완료를 기록할 수 있습니다[추론].
- **cancel:** todo는 cancelled로, doing은 `abort_requested`(cooperative)로 바뀝니다.
- **중복 방지:** `queueing_lock`은 todo 상태에서만 unique, `lock`은 doing 상태에서만 unique입니다(L100-102). 같은 key의 직렬화는 되지만 이력 전체에 걸친 idempotency는 아닙니다.

### PgQueuer
- heartbeat가 timeout(기본 30s)을 넘긴 picked job은 자동으로 다시 pick됩니다(L426-436).
- 문서가 "A recovered job will run again from the start. Ensure ... idempotent"라고 경고합니다([reliability](https://github.com/janbjorge/pgqueuer/blob/3064102fa7a478987aefb0ff2f6e0ed6d1adaaa0/docs/guides/reliability.md)).
- heartbeat UPDATE(L750-751)와 log_job DELETE(L682-716)가 모두 `id`로만 동작합니다.
- 그 결과 stale worker의 heartbeat가 다시 pick된 job을 계속 살려 두고, 둘 중 먼저 끝난 쪽이 row를 지웁니다[추론].
- `dedupe_key`는 queued/picked 상태에서만 unique입니다.

### DBOS
- 보장: workflow는 완료까지 실행되고, step은 at-least-once이며, transaction은 exactly-once입니다([tutorial](https://docs.dbos.dev/python/tutorials/workflow-tutorial) L281-283).
- exactly-once는 같은 DB 안의 transaction에만 해당합니다.
- 분산 복구는 executor_id 운영으로 하거나 hosted Conductor를 써야 합니다. Conductor는 API key가 필요하고, metadata-only 모드는 Teams 요금제부터입니다([Conductor](https://docs.dbos.dev/conductor/overview)). 회사 환경에서는 반출 경로가 됩니다.

### pgmq
- "exactly once delivery ... within a visibility timeout"이라고 홍보합니다(L17, L347).
- delete/archive는 `msg_id`만 받습니다. 그래서 vt가 지난 뒤 stale consumer가 다른 consumer가 처리 중인 메시지를 지울 수 있습니다[추론].

### 오해 방지
- **SQL row lock은 외부 LLM 쓰기를 fencing하지 않습니다.** `SKIP LOCKED` lock은 claim transaction이 끝나면 사라집니다.
- LLM 호출 동안 transaction을 열어 두는 것은 안티패턴입니다(긴 transaction, connection 점유, vacuum 지연). 그래도 외부 side effect는 막지 못합니다.

### 자체 최소 outbox [제안]
**table** `amm.job(job_id, kind, scope_key, idem_key, req_digest, state, attempts, not_before, lease_owner, lease_token bigint, lease_expires_at, cancel_requested, generation)`
- `UNIQUE(kind, scope_key, idem_key)`는 부분 index가 아니고 이력 전체에 걸칩니다.
- 같은 key인데 req_digest가 다르면 409를 반환합니다.

**동작**
1. **claim:** 짧은 transaction 안에서 CTE `SELECT … FOR UPDATE SKIP LOCKED`를 한 뒤 `UPDATE state='leased', lease_token=nextval(seq), lease_expires_at=now()+ttl`을 실행합니다.
2. **heartbeat:** `UPDATE … WHERE job_id AND lease_token=$t AND state='leased' RETURNING cancel_requested, generation`을 실행합니다. 결과가 0행이거나 cancel 요청이 있거나 generation이 다르면 worker가 스스로 중단합니다.
3. **commit:** 하나의 transaction에서 `UPDATE job SET state='succeeded' WHERE job_id AND lease_token=$t AND generation=current_epoch`을 실행합니다. 0행이면 ROLLBACK합니다. 통과하면 같은 transaction에서 파생 candidate, evidence link, receipt, 다음 outbox를 기록합니다.
4. **reaper:** lease가 만료된 job을 queued로 되돌리거나 dead로 표시합니다.

**외부 side effect**
- LLM 호출은 막을 수 없습니다. 중복 비용으로 계산합니다.
- Hindsight 쓰기는 `document_id=amm:{event}:{rev}`로 replace해서 idempotent하게 만들고, 사후 reconcile로 정리합니다.

**자체 구현을 택한 이유:** 표 1개와 SQL 약 5문장입니다. fence는 어차피 우리 commit transaction 안에 직접 써야 합니다. LGPL 의존도 생기지 않습니다.

## 5. Schema migration
- **Alembic:** `runtime/migration.py`에 advisory 같은 migration lock 장치가 없습니다(grep 결과 없음). 두 프로세스가 동시에 upgrade하는 것을 도구가 막아 주지 않습니다[근거+추론].
- `autocommit_block`은 앞선 작업을 무조건 commit합니다(L272-312). `transaction_per_migration`을 씁니다.
- session 수준 advisory lock은 transaction 의미를 따르지 않습니다([explicit-locking](https://www.postgresql.org/docs/18/explicit-locking.html) L175). 그래서 env.py에서 `pg_advisory_xact_lock`을 겁니다.
- **권한:** migrator role만 CREATE/ALTER EXTENSION을 할 수 있고 app role은 CREATE 권한이 없습니다.
- **Hindsight:** 자체 alembic(약 100개 revision)이 있고 `RUN_MIGRATIONS_ON_STARTUP`의 기본값이 true입니다. false로 두고 명시적으로 실행합니다.
- **호환 matrix:** amm release, Hindsight pin, PG major, pgvector 버전, tokenizer/model manifest를 함께 관리합니다.
- **방향:** forward-only입니다. binary를 되돌리는 것과 schema를 되돌리는 것은 다릅니다. 롤백은 이전 image + restore + tombstone 재적용입니다.
- **pgroll:** expand/contract와 이중 schema view 방식입니다. 단일 사용자 local에는 필요 없어 참고로만 둡니다.

## 7. Backup·restore·암호화
- **pg_dump:** 출력은 더 새로운 PG에 load할 수 있지만, 자신보다 새로운 PG server는 dump하지 못합니다([docs](https://www.postgresql.org/docs/18/app-pgdump.html) L495). schema 단위로 포함/제외할 수 있습니다. PITR는 아닙니다.
- **PITR(basebackup + WAL):** cluster 전체가 되돌아갑니다. 같은 cluster 안의 tombstone도 함께 되돌아갑니다. PG17+ incremental backup은 WAL summary와 이전 backup chain이 필요하고, 작은 DB라면 full backup이 더 단순합니다([L119-127](https://www.postgresql.org/docs/18/continuous-archiving.html)).
- **pgBackRest:**
  - 2.59.3 이전 버전은 RNG 오류 때 약한 subkey/salt를 만들 수 있었습니다. 업그레이드해도 이미 만든 subkey는 바뀌지 않으므로 새 stanza를 만들어야 합니다.
  - 유지보수가 2026-04-27에 중단됐다가 2026-05-18에 sponsor coalition으로 재개됐습니다.
  - 2.59.0부터 기본 설정에서는 root로 restore만 실행할 수 있습니다.
- **restic:**
  - 삭제는 forget 뒤 prune을 해야 합니다. prune 전까지 데이터가 남습니다.
  - `--max-unused`(기본 5%) 때문에 일부만 쓰이는 pack이 남습니다.
  - append-only 모드에서는 prune을 할 수 없습니다.
  - 살아 있는 PGDATA를 restic으로 직접 백업하면 일관성이 없습니다. dump 파일이나 pgBackRest repo를 백업합니다.
- **age:**
  - 수신자 공개키로 파일을 암호화합니다. `-pq` 옵션으로 post-quantum hybrid를 씁니다.
  - SSH 수신자를 쓰면 공개키 tag가 파일에 남아 추적할 수 있습니다(L291).
  - corpus마다 key를 따로 두고 key를 폐기하면 corpus 단위 crypto-shred가 됩니다. 항목 단위 삭제는 아닙니다.
- **tombstone barrier [제안]:**
  - ledger는 본문 없이 id, scope, digest, epoch, actor, 시각을 담고 hash-chain으로 잇습니다.
  - restore 단위 밖에 둡니다. logical dump라면 제외 schema에, PITR라면 별도 파일이나 cluster에 둡니다. 보존 기간은 데이터 backup 이상입니다.
  - restore 절차: 읽기 닫기 → restore → generation 증가(stale worker fence) → ledger 재적용과 파생물 purge → 검증 → 읽기 열기.
  - 'purge 완료'는 그 내용을 담은 모든 backup set이 만료된 뒤에만 기록합니다.
- **버전 제약:** 물리 backup은 restore할 때 같은 PG major와 같은 extension binary(pgvector .so)가 있어야 합니다. logical dump는 대상에 extension이 설치돼 있어야 합니다.

## 8. 로컬 배포·ingress·보안
- **설치:** native launchd를 쓰고 Docker Desktop은 요구하지 않습니다.
  - Homebrew에 postgresql@18 18.6과 pgvector 0.8.7 arm64 bottle이 있습니다.
  - [Postgres.app](https://postgresapp.com/extensions)은 pgvector를 포함합니다.
- **PG 접속:** Unix socket 또는 127.0.0.1에 scram 인증을 씁니다. role은 migrator, amm_app, amm_worker, hindsight_app, readonly로 나눕니다.
- **MCP SDK:**
  - 기본 host는 127.0.0.1입니다(mcpserver/server.py L1112).
  - host가 loopback일 때만 Host/Origin 보호가 자동으로 켜집니다(lowlevel/server.py L747-753).
  - 설정 없이 0.0.0.0에 bind하면 보호가 꺼집니다(transport_security.py).
  - 요청 body 기본 상한은 4MiB입니다.
  - Host/Origin 검사는 인증이 아닙니다. 같은 UID의 다른 프로세스도 접속할 수 있으므로 0600 token 파일과 TokenVerifier를 둡니다. stdio shim에서 UDS로 붙는 방식도 같은 UID 내 격리는 제공하지 않습니다.
- **내부 서비스:** Hindsight와 llama-server는 모두 loopback에 두고 key를 걸며 MCP와 webui는 끕니다.
- **이후 개인 VM:** Caddy로 TLS를 받고 OAuth를 거쳐 amm에 연결한 뒤, 나머지 서비스는 loopback에 둡니다. 대안은 Headscale private overlay입니다. Tailscale SaaS를 쓰면 metadata가 vendor 쪽으로 갑니다[추론].

## 9. 추가 엔진 채택 조건
- **OpenSearch + nori:** app tokenizer와 pg_bigm을 써도 한국어 형태소 품질 gate를 통과하지 못할 때만 고려합니다. 비용은 두 번째 저장소의 이중 쓰기, 삭제·restore·backup 부담, JVM 운영입니다.
- **graph DB:** multi-hop 질의 개선이 측정으로 입증될 때만 고려합니다.
- **Redis/Valkey/Qdrant:** 이 규모에서는 메울 능력 공백이 없어 쓰지 않습니다. 조사하지 않았습니다.

## 10. 우리가 직접 지켜야 하는 DB 불변식
1. `accepted`는 event, receipt, outbox가 같은 transaction으로 commit된 뒤에만 반환합니다. `accepted≠queryable`입니다.
2. idempotency key는 이력 전체에서 unique하고 digest를 함께 저장합니다. 재요청은 같은 receipt를 돌려받습니다. RPC id나 session id로 대신하지 않습니다.
3. lease token은 단조 증가합니다. 모든 파생 쓰기는 같은 transaction에서 `(job, token, generation)`을 검사합니다. 외부 효과는 idempotent하게 만들고 reconcile합니다.
4. 모든 읽기 경로에 eligibility를 적용합니다: 3 scope, approved revision의 exact digest, tombstone 미해당, watermark 충족. selector가 넓어지면 재승인을 받습니다.
5. tombstone ledger는 restore 단위 밖에 있고, restore barrier와 generation 증가를 거칩니다.
6. index manifest(model sha, 차원, 정규화, tokenizer_rev)가 같은 것만 함께 질의합니다.
7. arm별 status를 반환합니다. `unavailable≠empty`이며, 실패를 빈 결과로 위장하지 않습니다.
8. migrator 하나가 lock을 잡고 실행합니다. schema version이 맞지 않으면 앱이 시작을 거부합니다.
9. company와 personal은 다른 cluster, 다른 backup repo, 다른 key를 씁니다. 자동 sync는 없습니다.
10. 모델 route는 승인 ID에 묶습니다. route가 없으면 `blocked`이고 fallback은 없습니다.

# Local memory-service architecture

The product is an independent Python service. Agent Flow, Claude Code, Codex and omp are consumers, not runtime dependencies. Local and later personal cloud use one application contract; deployment changes credentials and network policy, not memory semantics.

## Boundaries

- **Edge:** official Python MCP SDK and authenticated local ingest/admin endpoints decode typed commands and call application handlers. Modern and legacy MCP invoke the same handlers. Protocol session IDs are not business identities.
- **Authority:** PostgreSQL transactions own source revisions, operation receipts, exact rule approvals, applicability, deletion heads and publication. Credential-bound principal/project/purpose are server authority; model arguments and client metadata are not.
- **Jobs:** one owner claims each durable job. Long model calls run outside DB transactions. Results publish only after checking the current lease/fence, source revision, authorization and deletion generation in the commit transaction.
- **Retrieval:** eligible evidence is filtered before model reasoning; final responses recheck eligibility. Recall presents citations and conflicts. Reflection remains a grounded candidate and cannot authorize rules. Transport wrappers do not create a second engine.
- **Rules:** deterministic selection and exact revision approval own the three applicability scopes: this local project, my projects within this deployment, team/project shared. A personal project rule does not require team publication. Relevant mandatory rules precede the first protected action; overflow or an unknown mandatory applicability boundary is an explicit refusal, not silent truncation.
- **Hosts:** opt-in adapters capture typed provenance and deliver bounded on-demand context. They keep per-agent/context-generation receipts and declare missing capabilities. Only supported hook paths can promise automatic invocation; model compliance and truth are not deterministic guarantees.
- **Operations:** installs modify receipt-owned project entries. Company data remains local; approved model execution is a separate route permission. Personal cloud is a later independent deployment, not company-data synchronization.

## Completion evidence

Exercise capture, extraction, recall, grounded reflection, correction/retraction and the next consumer read through the actual local service. Verify duplicate commands, scope denial, stale worker rejection, deletion/restore barriers, rule approval scope changes, failed capture visibility and bounded context. Native host, SDK-client, unit and source-only evidence are distinct. Read the run's implementation plan and SPEC coverage ledger for concrete acceptance scenarios.

## MUST AVOID

- Long rule bodies or full memory catalogs in root AGENTS.md/CLAUDE.md or connection-time instructions.
- A default/global project binding, model self-approval, optional search ranking as mandatory-rule enforcement, or a successful receipt before durable commit.
- Two queues independently owning the same work, stale publication after lease loss, or server-only deletion claims for context already delivered.
- Company-to-personal fallback, unapproved model/download/telemetry routes, or same-UID HOME directories presented as a security boundary.
- A notes-only or rules-only cutover, mock product proofs, source-only native compatibility presented as executed, or an unconfigured model route presented as a working full pipeline.
