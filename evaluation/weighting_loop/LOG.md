# 확장 가중치 루프 기록

규칙: `program.md`. 결과 표: `results.tsv`.

## 준비

- `Store.search_lexical(query_tokens=...)`와 `query_terms` CTE를 추가했다. `Application.context`는 질의 토큰을 따로 넘긴다.
- 동작 중립을 확인했다.
  - 원래 순위 SQL로 dev L0를 재면 질의별 결과가 의미 루프 baseline과 완전히 같다(186개 질의 × 3개 규모).
  - 확장 경로 무결성 테스트 6건(`tests/test_retrieval_expansion_weight.py`)이 통과한다. 이 테스트는 확장 단어로만 닿는 기억이 다음 경우 나오지 않음을 확인한다.
    - 철회·삭제
    - 다른 binding
    - 다른 realm
  - 기존 무결성 게이트 44건도 통과한다.
- holdout 확장 v2·v4(138개 질의)를 미리 만들어 동결했다.
- 실문서 확장(1,182개 질의)은 로컬에만 두고 commit하지 않는다. 동결 digest(sha256 앞 16자)는 v2 `f95f288a6e4cf938`, v4 `6f54f41d2d71796f`다.
  - 생성 agent는 안내문·질의 묶음·출력 파일 세 개만 다뤘다. 도구 호출 기록으로 검증했다.

## 결론: 확장 가중치 루프 (2026-10-21)

- 사전 등록한 탐색 공간(W 3개, R 2개)과 결과를 보고 만든 조합(R(0.75), R(1.25), I)을 모두 쟀다. keep을 통과한 후보는 없다. 그래서 승격 시도(holdout·실문서 판정)는 한 번도 하지 않았다. holdout과 실문서 결과는 보지 않았다.
- 순위는 원래 순위로 되돌렸다(`retrieval_ranking.py`). `query_tokens` 배관은 동작 중립이고 무결성 테스트가 붙어 있어 남겨 둔다.
- 가장 가까운 후보는 R(1)과 R(1.25)다.
  - 20배 의미 hit는 baseline 31에서 80–82로 늘었다(84개 중).
  - 키워드 hit는 줄지 않았다.
  - 둘 다 X4c 5배 키워드 MRR 하나에서 하한(0.588)을 0.003–0.011 차이로 넘지 못했다.
- 남은 하락의 원인: RRF에서 확장 가지가 표 하나를 더 준다. 그래서 질의·entity·확장 세 가지에 모두 걸리는 이웃 claim이, 질의만으로 1위였던 정답을 2위로 민다.
- 이 이상 dev에서 무게나 구조를 더 조정하면 하한 근처에서 dev에 맞추는 일이 된다. 그래서 여기서 멈춘다.
- 다음 결정은 사용자 몫이다.
  - 키워드 MRR 허용 하락을 바꾸고 R 후보를 holdout에 올릴지. 이는 규칙 변경이므로 holdout을 보기 전에 정해야 한다.
  - dense 측정. 모델 CDN이 막혀 있다.
  - 여기서 종료할지.
