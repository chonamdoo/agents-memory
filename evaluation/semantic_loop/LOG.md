## 중간 결론: agent 확장 경로 (2026-10-21)

- 깨끗하게 생성한 확장 네 번(X-v0, v2, v3, v4)은 모두 의미 질의를 크게 살렸다.
  - 20배 의미 hit 31 → 60–82(84개 중).
  - 키워드 hit도 줄지 않았다(93 → 99–102).
- 그러나 네 번 모두 20배 키워드 MRR이 0.564–0.576으로, 동결된 하한 0.580(기준 0.600 − 0.02)을 넘지 못했다.
- 안내를 바꿔도 하락이 다른 질의로 옮겨 갈 뿐 크기는 거의 같았다.
  - v2: 식별자 질의에서 하락
  - v3: 식별자 질의는 고쳤으나 구체적인 자연어 질의에서 하락
  - v4: 확장을 줄였으나 같은 수준
- 원인은 구조적이다. 운영 경로(`application.py`)가 확장을 질의와 한 토큰 집합으로 합치고, 순위는 겹친 토큰 수를 센다. 그래서 확장 단어가 원래 질의 단어와 같은 무게를 갖고, 이웃 claim이 정답을 1위에서 2–3위로 밀어낸다.
- 이 루프의 수정 허용 파일(`arms_config.py`, `expansion_guidance.md`)로는 이 구조를 바꿀 수 없다. 안내문만 계속 바꾸면 dev에 맞추는 일이 되므로 이 경로의 안내 조정은 멈춘다.
- 남은 선택지는 사용자 결정이 필요하다.
  1. 확장 무게를 낮추는 순위 변경을 별도 사전 등록 루프로 연다(예: 원래 질의의 순위를 먼저 두고 확장은 뒤에서 채우거나, 확장 토큰에 낮은 가중치). 운영 코드가 바뀌므로 무결성 게이트와 holdout 판정을 그대로 적용한다.
  2. dense/hybrid 측정. 모델 CDN(`us.aws.cdn.hf.co`, `cas-server.xethub.hf.co`)이 막혀 아직 측정하지 못했다.

## 재동결 (2026-10-21)

- 확장 가중치 루프(`evaluation/weighting_loop/`)를 준비하면서 `store.py`, `application.py`, `retrieval_ranking.py`(docstring)가 바뀌었다.
  - `query_tokens` 배관을 넣었다.
  - `query_terms` CTE를 추가했다.
- 원래 순위 SQL은 새 CTE를 읽지 않는다. dev L0를 다시 재 질의별 결과(hit, 첫 순위, 반환 수, decoy)가 저장된 baseline과 완전히 같음을 확인했다(`weighting_harness.py neutral`).
- 그래서 이 루프의 `frozen.json`을 다시 동결했다. 규칙과 baseline은 그대로다.
- holdout용 확장(`expansions/v2-holdout.json`, `v4-holdout.json`)은 확장 가중치 루프의 사전 등록에 따라 만들었다. 생성 방식은 dev와 같다(도구 제한 subagent, 정답이 겹치지 않는 묶음). 각 생성 agent는 안내문, 질의 묶음, 출력 파일 세 개 외에 아무 파일도 건드리지 않았다. 도구 호출 기록으로 검증했다.

## 적대적 리뷰 (hybrid, holdout 전)

- P0: 없음.
  - dense·hybrid는 `eligible`에만 join한다. 그래서 무결성은 구조적으로 보장된다.
  - 벡터 게이트도 실제로 작동한다. 모든 claim에 완전 일치 벡터를 주고, dense 가지에서 대상이 먼저 나오는지 확인한 뒤 배제를 검사한다. 그래서 그냥 통과하는 일이 없다.
- P1-1: 지연 3/3을 아직 채우지 않았고, 첫 측정은 순서 효과(먼저 돈 D 비교군이 색인을 데움)일 수 있다.
  - 이후 H 비교군만 두 번 더 쟀다: H-e5 118, 119ms.
  - 리뷰 제안대로 L0와 H-e5를 같은 실행에서 세 번 재 직접 비교한다. 같은 실행의 L0는 참고용이고, 판정 기준은 동결된 baseline 그대로다.
- P2 반영
  - 앞 절의 "저장소의 두 번째 방어선이 잡는다"는 과장이었다. 리뷰어가 우회 대조군을 모든 사례에 돌려 보니, 저장소 안에서 막히는 사례는 일부다.
    - 철회된 source, 정정, 다른 binding, pool 압박, 다른 snapshot, workspace는 저장소가 막는다.
    - 철회된 claim, revision drift, 만료, health, restore는 application 단계의 재확인(`CONTEXT_STALE`)만 막는다.
    - 다른 realm은 테스트 자체의 단언만 잡는다.
    - 측정 경로(`store.search_lexical`)의 방어는 `eligible` join 하나다. 이 join은 건전하므로 구멍은 아니다. 다만 우회 대조군을 모든 사례로 넓히는 일을 후속 과제로 남긴다.
  - 승격 전에 무결성 게이트와 관련 테스트를 먼저 따로 돌린다. 실패하면 promote를 호출하지 않는다(하네스는 게이트 실패에도 holdout을 평가하므로).
  - holdout baseline은 `store.py` 변경 전에 쟀다. holdout·실문서 L0가 질의별로 그대로인지 일치 여부만 센다. 결과 수치는 보지 않는다.
  - 실문서 바꿔 말한 질문 파일은 baseline 때와 같은 파일이다(재생성하지 않았다).
  - 승격 시도 사이에 RRF `k`, `dense_weight`, 순서(H-e5 → H-mini → H-potion)를 바꾸지 않는다.
  - 배경 claim 1·5·20배는 한 가지 문장 틀로 만들어 dense가 쉽게 구별한다. 그래서 20배 의미 이득은 실제보다 클 수 있다. 실문서 holdout이 이를 보는 실제 판정이다. PR에 쓴다.
  - 질의 임베딩 40ms는 batch 32의 평균이다. 운영에서 한 건씩 부르면 더 걸린다. 따로 잰다.

- 질의 1건 임베딩 시간(CPU, batch 1, dev 질의 60개)

  - MiniLM: p50 12ms, p95 15ms.
  - potion: p50 0.2ms, p95 0.3ms.
  - 운영 검색 지연에는 이 값이 더해진다.
  - 이 측정은 holdout L0 일치 확인과, 아마 지연 1회차의 앞부분과 동시에 돌았다. 겹쳤다면 1회차 값을 부풀리는 쪽이다.

## 결론: 의미 검색 루프 (2026-10-21) — 개선 없음

- 승격 3회가 모두 실패했다. 규칙대로 "개선 없음"으로 기록하고 멈춘다. PR은 만들지 않는다. 운영 순위는 바뀌지 않았다.
- 세 번 모두 공통으로 걸린 조건은 하나다. **실문서 heading 질의의 MRR이 떨어졌다**(H-e5 0.080, H-mini 0.193, H-potion 0.094). 이 질의는 정책 제목·POLICY ID·업데이트 요약으로 찾는 질의다. 벡터 가지가 RRF에서 같은 무게로 표를 주어, 제목·ID가 정확히 맞는 기억 앞에 뜻이 비슷한 다른 정책을 끼워 넣는다. 합성 holdout에서는 이 현상이 약했다. 실문서는 비슷한 정책이 많아 크게 드러났다.
- 의미 검색 자체는 분명히 좋아졌다.
  - 합성 holdout 의미 질의는 세 모델 모두 CI 하한이 0보다 크다(H-e5 평균 +0.94).
  - 실문서 바꿔 말한 질문은 H-e5가 recall +0.275(CI [0.19, 0.36])로 가장 컸다.
- agent 확장 경로와 확장 가중치 루프도 keep을 통과하지 못했다(`weighting_loop/LOG.md`).
- 남은 한계와 다음 결정
  - 실문서 holdout은 세 번 집계로 보았다. 이 결과를 보고 dense 무게나 RRF를 고치면 holdout으로 튜닝하는 셈이다. 이어서 진행하려면 새 실문서 holdout(다른 문서 묶음)과 새 사전 등록이 필요하다.
  - 바뀌는 쪽의 가설은 다음과 같다. 정확한 제목·ID·식별자 일치를 먼저 두고, 벡터는 lexical이 약할 때만 채운다. 예를 들어 lexical 상위 일치는 고정하고 남은 자리를 벡터로 채우는 방식이다. 이렇게 하면 heading 퇴행 없이 의미 이득을 지킬 수 있다.
  - 운영 비용
    - e5-large는 질의 1건 임베딩에 CPU p50 139ms가 들고, 정답이 없는 질의에도 늘 20개를 돌려준다.
    - potion은 0.2ms로 거의 공짜다. 다만 의미 이득이 더 작다(20배 의미 hit 52, H-e5는 78).
    - 회사의 로컬 ML 금지 제약과 함께 정책 결정이 필요하다.
  - 배경 claim은 한 가지 문장 틀이라 dense가 쉽게 구별한다. 그래서 합성 20배 결과는 실제보다 낙관적일 수 있다(리뷰 P2-6).

## 재현 절차: 새 DB에 다시 올릴 때 (2026-10-21)

- 평가 claim은 `Store.record`가 매기는 무작위 UUID를 ID로 갖는다. 순위 SQL은 점수가 같을 때 ID 순으로 자른다.
- 그래서 캐시 schema(`am_loop_*`)를 지우고 corpus를 새로 올리면, 순위 코드가 같아도 동점 claim의 순서가 바뀔 수 있다. 그러면 hit·MRR이 commit된 baseline과 달라질 수 있다.
- 이 LOG와 `results.tsv`의 모든 수치는 같은 PostgreSQL 인스턴스의 같은 캐시 schema에서 쟀다.
- 새 환경에서 다시 재려면 baseline부터 새로 잰다.
  - dev: `run --baseline`
  - holdout·실문서: `state/baseline-*.json`을 옮겨 두고 `baseline-holdouts`
  - 그 다음에 후보를 비교한다. 예전 baseline과 새 결과를 섞지 않는다.
  - `weighting_loop/weighting_harness.py neutral`은 이 불일치를 드러낸다.
