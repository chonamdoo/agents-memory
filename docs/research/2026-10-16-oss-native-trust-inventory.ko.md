# claude-mem 외 86항목의 Claude/Codex 설치·trust 처리 — 2026-10-16

## 결론과 증거 수준

**다른 OSS도 대개 native 동의를 없앤 것이 아니다.** 사용자 전역 MCP·hook 설정을 쓰거나 native plugin CLI에 설치를 위임한다. 일부는 명시적으로 MCP 도구를 자동 허용하지만 이것은 폴더 신뢰·플러그인 활성화·정확한 훅 정의의 hash 승인과 서로 다른 권한이다. 평가에서 trust/permission bypass를 쓴 결과를 생산 headless 설치 성공으로 제시할 수 없다.

기존 [86항목 목록](2026-10-15-oss-local-runtime.ko.md#전체-후보-판정표)의 **번호·literal identity·SHA를 유지**했다. 86은 고유 runtime 제품 수가 아니다. claude-mem은 별도 조사이며 native host 내부 구현인 #38 anthropics/claude-code, #39 can1357/oh-my-pi, #51 openai/codex는 여기서 재조사하지 않았다. 아래는 고정 source/doc 및 공개 issue/PR를 읽은 조사다. upstream 설치·코드 실행·build/test·설정/trust/후크 활성화·사용자 전역 config 및 비공개 trace 열람은 하지 않았다. 동적 issue 상태와 merged 여부는 조사 시점 관측이며 소스 존재·배포 artifact·native 실행 증거를 서로 바꾸지 않는다. 일부 GitHub API는 rate limit 403이어서 pinned raw와 공개 HTML을 사용했다. 관련 issue를 찾지 못했다는 말은 부재 증명이 아니다.

native host 자체의 정상 승인 API·실제 local metadata·우리 계약과의 채택 판단은 [통합 조사](2026-10-16-oss-native-trust.ko.md)를 따른다. 이 부록은 upstream 설치 source의 비교이며 해당 API를 호출하거나 사용자 설정을 바꾸는 절차가 아니다.

### 반드시 분리할 다섯 층

1. **폴더/project trust:** 저장소가 제공한 설정·코드 실행을 host가 신뢰하는가.
2. **marketplace/plugin 설치·enablement:** payload가 설치되고 해당 scope에서 활성화되는가.
3. **개별 native hook trust:** Codex의 현재 정의/경로/명령에 대한 정확한 host hash 승인이 있는가. Claude에도 같은 hash 승인 체계가 있다고 일반화하지 않는다.
4. **MCP 등록·개별 도구 권한:** 서버 연결과 mutating tool의 허가는 별개다. 자동 allow는 이 층의 확대일 수 있다.
5. **행동 집행:** 실제 protected action 시도·거절·부작용 0이 입증되는가. additionalContext, reminder, Stop 재요청, retrieval score, 이름 기반 safe 분류는 곧바로 이 보증이 아니다.

`user/global` 설정은 프로젝트 설정을 읽지 않는 특정 배치를 만들 수 있지만 **자동 우회도, 프로젝트 격리/egress 승인/required-action 집행의 보증도 아니다.** 아래에서 trust 쓰기 미발견은 검토한 installer/entrypoint의 한정된 소스 결과다.

## 6. 전화·headless에서 정직한 선택지

- **지금 가능한 것은 전화에서의 검토·범위 선택이다.** 설치할 payload/정확한 hook command·scope·MCP 도구 목록·data destination을 source로 비교하고, 승인할 대상과 유효기간을 좁힌 계획을 만들 수 있다. 이번 조사는 설치·활성화 동의가 아니며 사용자에게 데스크톱을 켜라고만 요구하지 않는다.
- **upstream의 agent-guided/plugin chat 설치도 사용할 수 있는 UI 형태이지 consent의 대체는 아니다.** effortless/autoharness 등은 chat input으로 marketplace/plugin 명령을 요청할 수 있다. 전화가 이미 인증된 해당 host session에 연결되어 있을 때의 조작 가능성과, 그 경로가 native folder/hook 승인을 실제 지원하는지는 다른 문제다. 후자는 별도 host 조사/API 증거가 필요하다. 문서의 “no terminal”을 “무승인 설치/실행”으로 번역하지 않는다.
- **MCP-only pull 방식은 hooks를 필요로 하지 않는 별도 기능 범위다.** 이미 올바르게 승인·project-bound된 서버라면 수동 recall/remember의 headless 경로를 논할 수 있다. 이 방식은 자동 capture·강제 pre-action read·native 보호를 제공했다고 주장할 수 없으며, 현재 memory system을 대체하거나 global scope로 넓히는 승인이 아니다.
- **무인 실행은 사전에 승인된 정확한 현재 설정 안에서만 가능하다.** 경로·payload 변경으로 hash가 달라지면 이전 승인 재사용을 가정하지 않는다. upstream agentmemory/Basic Memory/OSK/context-mode는 설치 뒤 native hook 검토를 남긴다. host가 현재 전화 경로의 안전한 승인을 제공하지 않는 항목은 **pending/unproven**으로 유지한다. 기존 trust file 위조, managed-policy 전환, broad global trust, permission/hook-trust bypass는 대안으로 제시하지 않는다.
- **원격 운영자를 통한 작업은 [INFERENCE] 가능한 운영 형태일 뿐 이번 소스에서 검증한 제품 기능이 아니다.** 이미 승인된 인증·전송 채널이 있을 때 별도 명시 동의로 정확한 hook/프로젝트만 검토하도록 요청할 수 있다는 뜻이다. 새 tunnel·service·remote transcript 수집·사용자 trust state 변경을 이번에 하지 않았다.
- **외부 API·cloud sync·LLM 판단·embedding·telemetry 전송은 native consent와 독립적인 별도 승인이다.** 전역 설치 또는 bearer 존재만으로 company/personal binding이나 approved egress가 생기지 않는다. 승인되지 않은 데이터 이동과 silent provider fallback은 계속 금지한다.

**종합:** OSS가 선택한 편의성 경로를 참고할 수는 있지만, 우리 실제 MCP protocol 성공·synthetic test와 native strict 보호의 실패/미입증을 섞지 않는다. 글로벌 설치로 guard를 피하거나 evaluator bypass를 생산으로 옮길 근거는 없다. 프로젝트 binding·원문/철회 authority·명시 egress·실제 action denial의 독립 검증 계약을 유지한다.
