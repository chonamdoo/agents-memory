**현재 권고는 A 유지와 기존 `procedure`·`rule_candidate`를 쓰는 절차 재사용 trial 지침입니다. 코어와 four tools는 지금 변경하지 않습니다.**

**3. 최종 순서와 선행관계**

제 권고 우선순위는 **A·기존 절차 재사용 trial → O3/O4 → O5 → B 확대 → C → D**입니다. 이것은 착수 우선순위이며, 모든 안 사이의 기술적 의존성을 뜻하지는 않습니다.

1. **Now: A와 기존 절차 재사용 지침**

   이미 있는 `procedure`·`rule_candidate`를 사용합니다. 관찰된 작업 조건과 결과를 구분하고, 재사용할 내용은 기존 exact revision 승인 경로로 검토합니다. 새 자동 consumer나 trace 수집기를 붙이지 않습니다. 1–2주 local trial은 아직 수행되지 않았습니다.

2. **After-trial: O3/O4 — 긴 본문 전달과 관련성 선택**

   optional overflow에 안전한 참조를 남기고 기존 `inspect`를 통한 bounded·paged read를 검토합니다. 페이지는 정확한 revision과 연결해야 합니다.

   optional 관련성 선택은 현재 eligibility를 통과한 집합 안에서만 합니다. required 규칙을 relevance 점수로 탈락시키면 안 됩니다. 필요한 required 본문을 예산 안에서 완전히 확인하지 못하면 protected action을 진행하지 않습니다. 빈 selector의 기존 `TRUE` 의미도 임의로 변경하지 않습니다.

3. **O5 — verified outcome과 다음 사용 연결**

   전체 tool trace부터 수집하지 않습니다. 먼저 제공된 rule revision·실행 대상 snapshot·확인 주체·검증 방법·관찰 결과를 좁게 연결합니다. 제공·소비·성공·인과효과는 구분하고, 같은 `root_run`의 재시도를 독립 근거로 세지 않습니다.

4. **B 확대 — bounded feedback, 이후 O6/O7/O8**

   B1의 재제안 억제는 별도로 평가할 수 있습니다. 그러나 “다음 사용이 좋아졌다”는 판단에는 O3/O4와 O5가 필요합니다.

   이후 **O6 개인 opt-in trace → O7 기존 procedure candidate 생성**을 검토합니다. O8 advisory scan은 검토 보조입니다. scan 통과는 사실 보증·승인·permission grant가 아닙니다.

5. **C와 D — 각자 별도 게이트**

   C는 코드 변경 때문에 잘못 적용된 사례와 관측 가능한 dependency가 있을 때 검토합니다. B 완성을 기다려야 하는 기술적 이유는 없습니다.

   D도 B/C 완성이 필수는 아닙니다. 다만 기본 우선순위는 낮습니다. 첫 시험은 ① 이 로컬 프로젝트, 공개·합성 자료, non-required, 작은 read-only 본문으로 제한하고 실제 host 동작을 따로 증명합니다.

**4. 지금 추가하지 않을 코드와 acceptance**

지금 추가하지 않을 범위는 feedback generation consumer, tool trace·`root_run` 수집, 자동 distiller, advisory scanner, dependency index, Skills endpoints입니다. BAML/Jev 의존이나 protocol 전면 rewrite도 거절합니다.

후속 구현의 acceptance는 다음 조건을 충족해야 합니다. **현재 통과한 것으로 간주하지 않습니다.**

| 분야 | 필요한 acceptance |
|---|---|
| **품질·효과** | 생성 원천과 평가 과제 분리, 독립 origin 구분, holdout·반례 보존. 같은 조건에서 다음 사용 정확성·누락·오선택·호출수 비교 |
| **비용·지연** | 실제 host metadata·본문 bytes와 tokens, 지연, 모델 비용, 승인자 시간을 함께 측정. 수치 기준은 trial 전에 확정 |
| **권한·삭제** | exact binding 변경·세 scope·required `UNKNOWN` 차단 검증. source 삭제·철회·revision 변경과 publish/delivery 경쟁 조건 검증 |

회사 corpus는 외부 model·telemetry·gateway·개인 cloud로 보내지 않습니다. 팀 모델 경로 승인은 별도 정책이며, 이 검토가 전송 허가를 추가하지 않습니다. 개인 cloud도 trial 이후의 별도 결정입니다.

**5. 남은 의견 차이와 미확인 사항**

- **B1의 순위:** Opus는 consumer를 먼저 붙입니다. 저는 긴 승인 본문의 전달·관련성 선택을 먼저 둡니다. consumer 부재의 전역 확인과 사용자가 기대한 feedback 계약은 미확인입니다.
- **D의 정확성:** 저는 selector 손실을 불가피하다고 보지 않습니다. 서버 gate로 보존할 여지는 있습니다. 실제 구현과 host 증거는 없습니다.
- **C의 가치:** 위험은 인정하지만, stamp-only 관측만으로 오적용을 얼마나 줄일지 모릅니다. 관측 레코드를 binding 밖에 둔다는 Opus 제안에는 동의합니다.

다음 결정 대상은 **새 기능 승인보다 기존 절차 재사용 trial의 범위와 성공 기준**입니다. 기존 로컬 실행 근거는 활용하되, 절차 증류 품질·장기 trial·Skills native 지원은 미확인으로 남깁니다.
